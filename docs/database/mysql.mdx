MySQL is supported. Use it when you already run MySQL or a MySQL-compatible cloud database. The adapter uses [`mysql2`](https://github.com/sidorares/node-mysql2) and emulates features MySQL lacks (`RETURNING`, `ILIKE`) on top of the shared `DrizzleAdapter` core.

> **MySQL is second-class to PostgreSQL in Nextly.** Some features Nextly relies on -- savepoints, JSONB, array types, native `ILIKE`, native `RETURNING` -- either don't exist or are emulated. PostgreSQL is the recommended production database; pick MySQL only if it is already part of your stack. See the [feature comparison](/docs/database#feature-comparison).

> **Minimum version: MySQL 8.0.** Older real MySQL hard-fails at connect with a clear upgrade pointer. MySQL-compatible variants (MariaDB, TiDB, Aurora MySQL, PlanetScale, Vitess) warn and proceed -- see [database support](/docs/database/support) for the variant policy.

## Configuration

Set `DB_DIALECT=mysql` and `DATABASE_URL` in your environment.

```bash title=".env"
DB_DIALECT=mysql
DATABASE_URL=mysql://nextly:nextly@localhost:3306/nextly_dev
```

### Programmatic usage

```typescript title="src/db.ts"
import { createMySqlAdapter } from "@nextlyhq/adapter-mysql";

const adapter = createMySqlAdapter({
  url: process.env.DATABASE_URL!,
});

await adapter.connect();
```

Or pass discrete fields:

```typescript
const adapter = createMySqlAdapter({
  host: "localhost",
  port: 3306,
  database: "nextly_dev",
  user: "nextly",
  password: "nextly",
});
```

## Charset and collation

MySQL's default `utf8` is a 3-byte subset of UTF-8 that doesn't store emoji or many CJK characters. Use `utf8mb4` for everything Nextly stores. The adapter does **not** force a charset by default -- set it on the connection:

```typescript
const adapter = createMySqlAdapter({
  url: process.env.DATABASE_URL!,
  charset: "utf8mb4",
});
```

For a freshly created database, configure the server-level defaults too:

```sql
CREATE DATABASE nextly_dev
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

The Docker setup at the repo root already runs MySQL with `--character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci`.

## Connection pool

The adapter uses `mysql2`'s built-in pool. Defaults:

| Option                     | Default | Description                                                             |
| -------------------------- | ------- | ----------------------------------------------------------------------- |
| `pool.max`                 | `10` (`3` on Vercel) | Maps to `mysql2`'s `connectionLimit`. Maximum simultaneous connections. |
| `pool.min`                 | `0`     | Connections kept open however long they are idle. Like PostgreSQL's `pool.min`, it is how many of the connections the pool has opened it keeps: the pool does not open connections ahead of demand to reach it. |
| `pool.idleTimeoutMs`       | `30000` (`5000` on Vercel) | How long a connection above `pool.min` may stay idle before it is closed, checked once a second. `0` keeps every idle connection open. |
| `pool.connectionTimeoutMs` | `15000` | How long a request waits in the queue while every connection is in use. Past it the request fails as `DATABASE_BUSY` (503, `Retry-After: 5`); `0` leaves that wait unbounded. Also the time a new connection gets to open (`mysql2` `connectTimeout`): one that cannot open in time fails as a connection error, not as busy. |

```typescript
const adapter = createMySqlAdapter({
  url: process.env.DATABASE_URL!,
  pool: {
    max: 20,
    idleTimeoutMs: 30000,
    connectionTimeoutMs: 10000,
  },
});
```

`mysql2`'s own idle closing cannot keep a minimum: it closes every connection idle past its `idleTimeout`, and only when `maxIdle` is set below `connectionLimit`. So the adapter sets `maxIdle` equal to `connectionLimit`, which keeps `mysql2` from closing idle connections by itself, and closes them itself: past `pool.idleTimeoutMs`, least recently used first, down to `pool.min`. These are the settings and the defaults the PostgreSQL adapter uses on a server, so `pool` and the `DB_POOL_*` variables mean the same pool on both.

Needs the release after 0.0.2-alpha.78. Before it the pool closed no idle connection outside Vercel and ignored `pool.min`, so a server kept every connection it had opened. To keep connections open as before, set `pool.min` to the pool's maximum (`DB_POOL_MIN=10` with the default maximum, or the same value as `DB_POOL_MAX`), or set `pool.idleTimeoutMs: 0` in code.

The pool is configured with `waitForConnections: true`: a request that finds every connection in use waits in the queue for a free one, for at most `pool.connectionTimeoutMs`. The queue has no length limit (`queueLimit: 0`); each wait in it is bounded instead. A connection that frees up after its request gave up goes straight back to the pool.

### On Vercel

On Vercel (where `VERCEL` is set) the pool defaults to `max: 3`, `min: 0` and `idleTimeoutMs: 5000`, so every connection idle for 5 seconds is closed. A Vercel function instance is suspended between requests and keeps the connections it holds open while suspended, so a small pool that closes idle connections quickly keeps a small database within its connection limit. Each setting you give, in `pool` or as a `DB_POOL_*` env var, replaces only its own default.

When [`@vercel/functions`](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package#attachdatabasepool) is installed in the app, the adapter also hands its pool to `attachDatabasePool`, which keeps an instance alive until its idle connections have closed. It is an optional peer dependency: without it the adapter logs one warning at connect. See [Database connections on Vercel](/docs/guides/deployment#database-connections-on-vercel).

## SSL / TLS

System health on the dashboard reads whether the connection is actually encrypted; see [Encrypted connections](/docs/database/encrypted-connections).

For production, enable SSL:

```typescript
const adapter = createMySqlAdapter({
  url: process.env.DATABASE_URL!,
  ssl: { rejectUnauthorized: true, ca: process.env.CA_CERT },
});
```

`ssl: true` enables SSL with driver defaults; `ssl: false` (or omitted) disables it. The full `SslConfig` shape (`rejectUnauthorized`, `ca`, `cert`, `key`) is the same as the [PostgreSQL adapter](/docs/database/postgres#ssl-tls).

## MySQL-specific options

| Option               | Type          | Default          | Description                                                                                    |
| -------------------- | ------------- | ---------------- | ---------------------------------------------------------------------------------------------- |
| `charset`            | `string`      | (driver default) | Connection charset. Set to `utf8mb4` for full Unicode.                                         |
| `timezone`           | `string`      | `'local'`        | Timezone for date handling, e.g. `'+00:00'`.                                                   |
| `multipleStatements` | `boolean`     | `false`          | Allow multiple statements per query. Off for SQL-injection safety; the adapter forces `false`. |
| `dateStrings`        | `boolean`     | `false`          | Return dates as strings instead of `Date` objects. The adapter forces `false`.                 |
| `queryTimeoutMs`     | `number` (ms) | `15000`          | Default for the adapter's internal timeout helpers.                                            |

```typescript
const adapter = createMySqlAdapter({
  url: process.env.DATABASE_URL!,
  charset: "utf8mb4",
  timezone: "+00:00",
});
```

## Differences from PostgreSQL

The adapter handles each of these automatically, but they are worth knowing:

- **No `RETURNING`.** After `INSERT`, the adapter issues a follow-up `SELECT` (using `insertId` for auto-increment, otherwise filtering by inserted column values) to return the row. Bulk inserts return rows by reading `result.insertId..result.insertId + affectedRows - 1`.
- **No savepoints.** The MySQL adapter sets `savepoint`, `rollbackToSavepoint`, and `releaseSavepoint` to `undefined` on the transaction context for safety. Nested transactions are not supported.
- **No native `ILIKE`.** Case-insensitive search is rewritten to `LOWER(column) LIKE LOWER(value)`.
- **No JSONB.** MySQL has a native `JSON` type but no JSONB-style binary-indexed variant.
- **No array types.** Store arrays as JSON.
- **Upsert needs a table with one unique key.** MySQL has no `ON CONFLICT (columns)`: `ON DUPLICATE KEY UPDATE` fires on a collision with any unique key, so it can't be held to the columns you name. The adapter's `upsert` therefore accepts a table only when its conflict columns are its one unique key besides the primary key. On any other table, it refuses before writing and names the other unique keys. There, insert and update inside a `transaction()` instead. On a table it accepts, `upsert` means what it does on PostgreSQL and SQLite: the row is inserted, or the existing row with that key is updated (or kept, when no column is left to update), and the stored row is returned. The conflict columns must be given values, and a conflict is resolved on the values you give: a `BEFORE INSERT` trigger that rewrites the key onto another row's value is refused as a unique violation rather than resolved onto that row.
- **Backtick identifiers.** MySQL uses `` `name` `` instead of `"name"`.
- **`?` placeholders.** MySQL uses positional `?` instead of `$1`, `$2`.

See the full feature matrix on the [database overview](/docs/database#feature-comparison).

## Deadlock retry

Transaction failures with MySQL error code 1213 (`ER_LOCK_DEADLOCK`) automatically retry when you opt in via `transaction()` options:

```typescript
await adapter.transaction(
  async tx => {
    await tx.insert("orders", orderData);
    await tx.update("inventory", stockUpdate, where);
  },
  {
    retryCount: 3,
    retryDelayMs: 100, // exponential backoff: 100ms, 200ms, 300ms
  }
);
```

Lock-wait timeouts (error 1205) and other failures are **not** retried -- they surface immediately so callers can decide what to do.

## Migrations

MySQL uses the same forward-only migration CLI as the other dialects:

```bash
pnpm nextly migrate:create --name=add-posts-table
pnpm nextly migrate:status
pnpm nextly migrate:check
pnpm nextly migrate
pnpm nextly migrate:fresh   # destructive, local-dev only
```

> **Rolling back.** `nextly migrate:down` rolls back the most recently applied migration using its `-- DOWN` section; there is no `migrate:rollback`. For anything else, write a new corrective migration. See [production migrations](/docs/guides/production-migrations).

## Local development with Docker

The repo's `docker-compose.yml` includes a MySQL profile. Start it with:

```bash
docker compose --profile mysql up -d mysql
```

That uses the same image and config as below. To run MySQL standalone:

```yaml title="docker-compose.yml"
services:
  mysql:
    image: mysql:8.0
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: dev_password
      MYSQL_DATABASE: nextly_dev
      MYSQL_USER: nextly
      MYSQL_PASSWORD: dev_password
    command: >
      --default-authentication-plugin=mysql_native_password
      --character-set-server=utf8mb4
      --collation-server=utf8mb4_unicode_ci
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:
```

```bash
docker compose up -d mysql
```

```bash title=".env"
DB_DIALECT=mysql
DATABASE_URL=mysql://nextly:dev_password@localhost:3306/nextly_dev
```
