title: ISR and caching
description: Cache your content pages and revalidate them the moment content changes. Tag reads with nextlyTags/cachedFind and Nextly busts them on every write.
---

Nextly turns every content change into a cache invalidation. Tag a page's data
with the collection/entry it reads, and a create, update, publish, unpublish,
delete, or slug change busts exactly those tags — the page regenerates on the
next visit, with no rebuild and no `force-dynamic`.

This is [Next.js Incremental Static Regeneration](https://nextjs.org/docs/app/guides/incremental-static-regeneration)
driven by your content, not a timer.

## How it works

1. A read tags its cached data with the `nextly:*` tags for the collection (and,
   for a detail page, the entry id).
2. A write computes the same tags and, after it commits and before it
   responds, expires each one, so any page tagged with them is invalidated.
   In a Server Action it calls Next's `updateTag`, so the person who made the
   change sees it on their next read. Everywhere else (a Route Handler, the
   admin API) it calls `revalidateTag(tag, { expire: 0 })`.

The write side is automatic once the admin route is wired (see below). You only
add the read-side tags.

## Enable it

Register the adapter once per server process. The most reliable place is Next's
[`instrumentation.ts`](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation),
whose `register()` runs at startup, before any route, Server Action, or
serverless worker handles a request — so **every** write context busts tags,
not just the ones that happen to have loaded the admin route:

```ts
// src/instrumentation.ts in a project with a src/ directory (every scaffolded
// project); instrumentation.ts at the project root otherwise. Next.js ignores
// the file anywhere else, silently.
export async function register() {
  // Node.js only: the adapter loads `next/cache` with `createRequire`, which
  // the edge runtime does not have.
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { registerNextCacheRevalidator } = await import("nextly/runtime");
    registerNextCacheRevalidator();
  }
}
```

Mounting the admin route handler also registers it, which is enough if every
content write goes through the admin API in the same process:

```ts
// src/app/admin/api/[[...params]]/route.ts
import nextlyConfig from "../../../../../nextly.config";
import { createDynamicHandlers } from "nextly/runtime";

export const { GET, POST, PUT, PATCH, DELETE, OPTIONS } = createDynamicHandlers(
  {
    config: nextlyConfig,
  }
);
```

If you write content through the Direct API (`nextly.create(...)`) from a Server
Action, a custom route, or the admin API, register from `instrumentation.ts` as
above — relying on the admin route alone leaves those contexts on the no-op
revalidator, and their writes would not refresh cached pages. A write in a
context with no adapter registered is a silent no-op for revalidation (never an
error), so it is safe but stale.

### Writes outside a request

Automatic revalidation fires for a write that runs **inside a Next.js request or
render** — a Route Handler, a Server Action, or the admin API. That is where
Next.js can expire a tag, and it covers how content is normally edited.

A write from **outside** a request — a cron job, a CLI, or a background worker
with no request in flight — cannot expire a tag through Next.js: it has no
cache scope to invalidate there. The write still succeeds, and Nextly records
its tags in the database, in a table `nextly migrate` creates:

- **With Nextly's cache handlers installed** (see Cache Components below),
  every instance reads that record and stops serving the previous version
  within about five seconds, whichever process made the write.
- **Without them,** Next.js's own cache never reads the record. A write made
  in the app's own process is expired there with the next write that runs
  inside a request, and Nextly logs one line per process the first time that
  happens. A write from a separate process, such as the CLI or another
  instance, does not reach the app's cache, so in production Nextly keeps
  every cached public read for at most a minute and refreshes it then. The
  first read after that minute may still get the previous version while it
  refreshes. Nextly logs one `cache-handlers-not-shared` line per process when
  this bound is in force. To refresh pages straight away and keep longer
  lifetimes, install the handlers, or run the write in a Route Handler or a
  Server Action.

### When the new version shows

- **Server Action:** the expiry completes before the action returns, and
  `updateTag` lets the person who made the change read it straight away.
- **Route Handler and the admin API:** the expiry starts before the response is
  sent and completes in the same invocation. A request made after the response
  arrives reads the new version. A request already in flight while the write
  ran may still read the previous one.
- **Other instances:** with Nextly's cache handlers installed (see Cache
  Components below), every other instance stops serving the previous version
  within about five seconds. They treat the expiry as standing for one second
  past the write, the time an instance may keep a collection's settings
  cached, so a page one of them rebuilt from settings it read just before a
  schema change is not served either. That second is the whole cost: a tag
  written more than about once a second keeps the other instances rebuilding
  the reads that carry it until the writes pause, while the instance making
  the writes is not affected.

### If an expiry fails

A tag that fails to expire is retried once. If it fails again, the write still
succeeds: Nextly logs the tags and expires them with the next write in a
request, and the REST and admin response says so with a notice. If the database
refuses the record that tells other instances, Nextly also retries that on its
own: after 1 second, then waiting twice as long each time up to 30 seconds, and
at the process's next cached read. Other instances then see the write within
about a minute of the database answering again, and on serverless within a
minute of the next invocation. It logs one line when these retries start and
one when they succeed. The notice looks like this:

```json
{
  "warnings": [
    {
      "severity": "notice",
      "phase": "cache-expiry",
      "collection": "posts",
      "code": "CACHE_EXPIRY_DEFERRED",
      "message": "The change is saved. Its public pages may show the previous version for a while."
    }
  ]
}
```

The Direct API's mutations return the same notice in the result's `warnings`, so a caller can tell the expiry was deferred.

### Which writes expire a page

Every write that changes what a read returns:

- creating, updating, publishing, unpublishing and deleting an entry, and a
  slug change;
- saving a Single;
- a release that publishes or unpublishes its documents;
- deleting a collection or a Single;
- a plugin writing to columns it added to a collection, a Single or a component
  with `ctx.db.contributed(...).set`. A component's row expires the entry or
  Single it sits in. Inside `ctx.db.transaction` the expiry waits for the
  commit, and a rolled-back write expires nothing.

## Tag a read

Use `cachedFind` to cache a data read and `nextlyTags` to tag it:

```tsx
// app/(site)/blog/[slug]/page.tsx
import { getNextly } from "nextly";
import { cachedFind, nextlyTags } from "nextly/runtime";

import config from "../../../../nextly.config";

export default async function Post({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const nx = await getNextly({ config });

  const post = await cachedFind(
    async () => {
      const { items } = await nx.find({
        collection: "posts",
        where: { slug: { equals: slug }, status: { equals: "published" } },
        limit: 1,
      });
      return items[0] ?? null;
    },
    { tags: nextlyTags("posts"), keyParts: ["posts", "detail", slug] }
  );

  if (!post) return null;
  return <article>{/* ... */}</article>;
}
```

Publishing or editing any post now busts `nextly:posts` and this page
regenerates. For a listing page, tag it the same way — `nextlyTags("posts")` —
and it revalidates on any change in the collection.

### `nextlyTags(collection, id?, locale?)`

Builds the tags a read should carry:

- `nextlyTags("posts")` — the collection tag; for lists, indexes, sitemaps.
- `nextlyTags("posts", id)` — adds the entry-id tag; for a detail page, so a
  change to that one entry invalidates it. Tags by the **immutable id**, so a
  slug rename or a status change still invalidates.
- `nextlyTags("posts", id, locale)` — adds the per-locale id tag.

A detail read intentionally carries the collection tag too, so it also refreshes
when the collection changes around it. Because a match on **any** tag
invalidates the entry, that broadens invalidation: any change in the collection
(or any locale of the entry) refreshes the read, rather than only that one
locale's page. That is safe — a stale read is never served, only re-fetched more
often. If you need strictly per-entry or per-locale granularity on a
high-traffic route, tag with the entry/locale tag alone rather than this helper's
broad, safe default.

For a singleton (global) use `nextlySingleTags("header")`.

## Security: caching a per-user read

`cachedFind`'s `keyParts` decide which requests share a cache entry. **Include
anything the result varies by** — and for a read that applies per-caller access
rules (a code-defined `access.read` that reads the caller's roles or
permissions, an API key's narrowed scope), that means the caller's identity:

```tsx
// Per-user list — the caller's id is in the key, so it never leaks.
declare const user: import("nextly").UserContext;
// `nx` is the instance the page obtains above, inside its own component. Each
// fence here stands alone, so it is declared rather than assumed in scope.
declare const nx: Awaited<ReturnType<typeof import("nextly").getNextly>>;

const mine = await cachedFind(() => nx.find({ collection: "orders", user }), {
  tags: nextlyTags("orders"),
  keyParts: ["orders", "list", user.id], // <-- caller identity
});
```

If you cache an owner-filtered read under a stable key that omits the caller, two
different users share one cache entry and one is served the other's rows — a
cross-tenant data leak, not a stale-cache annoyance. For genuinely public content
(the same for every reader, like a published blog post) a stable key is correct
and gives the full caching benefit.

## Opt out of revalidation

A collection or Single whose pages manage their own freshness can opt out with
`revalidate: { disable: true }` in its config. None of the writes above then
expire its tags, a delete or a plugin's write included. One exception: when a
write cannot read the setting, because the record is already gone or the
registry cannot be reached, it expires the derived `nextly:*` tags anyway. An
extra cache miss is the cheaper mistake; a page left stale is the worse one.

A bulk import, seed, or CLI write that owns its own cache strategy can skip the
per-row revalidation with `disableRevalidate`:

```ts
await nx.create({ collection: "posts", data, disableRevalidate: true });
```

The write still records its outbox event (webhooks and retention are
unaffected); it just does not bust any cache tags.

## Cache Components

Nextly runs with Cache Components and Partial Prefetching on. An app made by
`create-nextly-app` has both, and so does one it joins, unless that app's
config can't be changed safely: then the report prints the lines to add
([Installation](/docs/getting-started/installation#cache-components)). Three
things keep its cached reads fresh; with only some of them, a page read right
after a write can still show the previous version. A new blog has all three. An
app made by an earlier Nextly release, which turned Cache Components off, needs
each of them.

1. **Read through the app's own `"use cache"` function.** Once Cache Components
   is on, Next.js caches non-fetch reads with `"use cache"` and `cacheTag`, and
   the directive works only in code Next.js compiles. A scaffolded blog keeps
   that function in `src/nextly/cached-read.ts`. In a blog made by an earlier
   release that file is a stub that registers nothing: replace it with this.

   ```ts
   // src/nextly/cached-read.ts
   import { cacheLife, cacheTag } from "next/cache";
   import { registerCachedRead, runRegisteredRead } from "nextly/runtime";

   export async function cachedRead(
     key: string,
     tags: string[],
     revalidate: number | false
   ): Promise<unknown> {
     "use cache";
     cacheTag(...tags);
     // `revalidate: false` is tag-only, as everywhere in Nextly: only a write
     // expires the entry, never time. Next.js's "max" profile revalidates monthly.
     if (revalidate === false) {
       cacheLife({ revalidate: Infinity, expire: Infinity });
     } else {
       cacheLife({ revalidate, expire: Math.max(revalidate * 2, 60) });
     }
     return runRegisteredRead(key);
   }

   registerCachedRead(cachedRead, process.env.__NEXT_CACHE_COMPONENTS);
   ```

   Import it from every module that reads content through `cachedFind`; the
   blog's query modules (`src/lib/queries`) already do. Nextly passes the
   function only the read's key, tags and lifetime, which `"use cache"` can
   cache, and runs the reader itself. Register it from a module Next.js
   compiles as a server component: a copy imported from `instrumentation.ts`
   is not a cached function. A read with `revalidate: false`, the default, is
   cached until a write expires one of its tags, as with Cache Components off;
   one with a number of seconds is served stale past it and refreshed in the
   background. Outside a request or build, in a script or a background job,
   the read runs directly, uncached.
2. **Install Nextly's cache handlers** in `next.config.ts`. Next.js's default
   incremental cache serves a page's previous shell once after its tags are
   expired, so the first read after a write would still be the old version:

   ```ts
   cacheComponents: true,
   partialPrefetching: true,
   cacheHandler: require.resolve("nextly/cache-handler"),
   cacheMaxMemorySize: 0,
   cacheHandlers: { default: require.resolve("nextly/cache-handlers") },
   ```
3. **Keep `createRegister`'s `cacheComponents` value** in `instrumentation.ts`
   (`process.env.__NEXT_CACHE_COMPONENTS`). Nextly, loaded from
   `node_modules`, learns the setting only from it: with it off, Nextly warns
   once at start; with it on and no read function registered, Nextly warns at
   the first cached read and keeps using `unstable_cache`.

With Cache Components off, which Nextly does not support, Next.js refuses to
build a `"use cache"` function, so a blog with it off needs the stub that
registers nothing (`export {};`) in place of this file, and its reads are
cached with `unstable_cache`.

## Notes

- Works across the supported Next.js range (see
  [Requirements](/docs/getting-started/installation#requirements)) on the stable
  `revalidateTag` / `unstable_cache` primitives.
- `cachedFind` runs the reader directly (no caching) outside a Next runtime, so
  the same code works in tests and non-Next callers.
- Add `revalidate: <seconds>` to `cachedFind` for a time-based safety net on top
  of tag-based busting.
- Next.js keeps at most 128 tags on one cached read and drops any tag longer
  than 256 characters. `cachedFind` leaves out the over-long tags, keeps each
  tag once in the order you give, and leaves off any past 128 with a warning
  logged once. The routes Nextly provides put their own collection's or
  Single's tag first, so a read that lists many related collections still
  expires whenever its own content changes. A read that
  lists many related collections still expires whenever its own content
  changes.
