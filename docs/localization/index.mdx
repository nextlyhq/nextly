---
title: Localization
description: Run the same site in several languages, with a fallback when a translation is missing, and publish each language separately.
---

Localization lets one document exist in several languages. An editor switches language at
the top of the edit screen and writes the Spanish version of the same post, without
creating a second post.

## Availability

|            |                                                                 |
| ---------- | --------------------------------------------------------------- |
| Built in   | No plugin required                                              |
| Admin      | Language switcher on edit screens, plus a translations overview |
| Permission | The same access as editing the document                         |

## Turn it on

Declare your languages once, in `nextly.config.ts`:

```ts
import { defineConfig } from "nextly";

export default defineConfig({
  localization: {
    locales: [
      "en",
      { code: "es", label: "Español" },
      { code: "ar", label: "العربية", rtl: true },
      { code: "fr", label: "Français", fallbackLocale: "en" },
    ],
    defaultLocale: "en",
    fallback: true,
  },
});
```

A locale is either a bare code or an object. The object form carries:

| Key              | Meaning                                          |
| ---------------- | ------------------------------------------------ |
| `code`           | The locale code, e.g. `es`                       |
| `label`          | What the admin shows in the language switcher    |
| `rtl`            | Renders that language right-to-left              |
| `fallbackLocale` | Which language (or ordered list) to fall back to |

### Or keep the list out of your code

Leave the `localization` block out, and the site's languages are stored in its database instead,
managed through the languages API. The admin has no screen for them yet. A site starts with one
language, English, and nothing is stored until a change is made.

| Request                                | What it does                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------- |
| `GET /api/languages`                   | Lists the languages, removed ones included: `{ items, meta }`, with `meta.lockedByConfig` |
| `GET /api/languages?defaultPreview=fr` | Says how many translations each language holds, before French becomes the default         |
| `POST /api/languages`                  | Makes one change, named by `kind`: `add`, `update`, `reorder`, `remove` or `setDefault`   |

```json
{ "kind": "add", "code": "fr", "label": "Français", "fallback": ["en"] }
```

- Codes are BCP 47 (`fr`, `pt-BR`) and unique whatever their letter case.
- Removing a language keeps its content: it stops being served, other languages' fallback lists
  skip it, and adding it back restores it. The default language cannot be removed.
- Making another language the default must be confirmed (`"confirmed": true`), moves no content,
  and is refused while the current default has unpublished changes.
- Reading needs the settings read or manage permission; changing needs update or manage.

A `localization` block in `nextly.config.ts` always wins: the list is then read-only through the
API. A language added on one server is served by every other server within a second.

## Choose what gets translated

Mark a whole collection localized, then opt individual fields out:

```ts
import { defineCollection, text } from "nextly/config";

export const Posts = defineCollection({
  slug: "posts",
  localized: true,
  fields: [
    text({ name: "title" }),
    // Not worth translating: the same value in every language.
    text({ name: "externalId", localized: false }),
  ],
});
```

Fields inherit the collection's setting, so the common case is one flag.

### When a field stops being translated

Changing a translated field to shared keeps its content, for a collection, a Single or a field group, whether you change it in the Schema Builder or in code:

- The default language's value becomes the field's shared value.
- Every other language's value is copied to the localization archive (the `nextly_i18n_archive` table) before the translated column is removed.

In code, set `localized: false` on the field and run `nextly migrate:create`. It writes three files that `nextly migrate` runs in order: one that writes the other languages to the archive, the migration that gives the main table the field's column, and one that copies the default language's value into it and removes the translated column. Rolling them back with `nextly migrate:down` puts the translated field back, every language included. `nextly migrate --dry-run` shows all three before anything runs.

If the archive cannot be written, the change is refused and nothing is changed. A field marked Required or Unique cannot stop being translated in the same change: turn the setting off and save, make the field shared and save, then turn the setting back on. In code the steps are the same, with `migrate:create` after each.

To bring those values back, make the field translated again, then restore that field:

```bash
npx nextly i18n:restore --collection posts --field title
```

`--collection` takes the slug of a collection, Single or field group, and `--field` takes the field's name or its column name. `--locale es` restores one language only. A field group can share its slug with a collection or a Single, and each one's archived values stay its own: when the slug names more than one, say which with `--kind collection`, `--kind single` or `--kind field-group`. The archive keeps the values until you remove them: add `--purge` to a restore to delete the rows it replayed. Deleting the collection, Single or field group also removes its archived values.

Values archived by a version of Nextly from before the archive recorded which kind of entity they belong to are matched to their entity when the slug names only one, and only from the time that entity was created. Any the archive can't match are kept, never deleted, and a restore of that slug says how many there are. Restoring with `--kind` also brings those values back as that entity's.

### When a shared field becomes translated

Changing a shared field to translated keeps its value too, for a collection, a Single or a field group, in the Schema Builder or in code. The value becomes the default language's translation, and the other languages start empty, to be translated.

In code, set `localized: true` on the field (or remove `localized: false` from a text field) and run `nextly migrate:create`. It writes one file, which adds the translated column, copies each entry's value into the default language, and removes the shared column. Rolling it back with `nextly migrate:down` makes the field shared again with the default language's value, and writes the other languages to the archive, as when a field stops being translated.

A field whose type, length or precision changes in the same change is refused, because its value would be copied into a column of the new shape: save the new type with the field still shared, then make it translated.

### When your migrations predate the record of translated fields

Snapshots written by early versions of Nextly don't record which fields are translated, and neither do the localization migration files from that time. When the snapshot doesn't say, `nextly migrate:create` reads it from the localization files that do. When neither says, and a change could move a field between translated and shared, `migrate:create` refuses and writes nothing, because guessing either way could lose the field's values. It names the fields. Changes that move no field go through as usual.

To record the translated fields, take two steps:

1. Undo the change in your config, so it matches what was last migrated, and run:

   ```bash
   npx nextly migrate:create --record-snapshot
   ```

   It writes a migration that changes nothing when it runs or rolls back, and a snapshot that records which fields are translated. Commit both. Run again with nothing new to record, it writes nothing. It's refused while the config has changes to migrate.

2. Make the change again and run `npx nextly migrate:create --name <name>`.

### When a translated field is renamed

Renaming a translated field in the Schema Builder keeps every language's value under the new name, for a collection, a Single or a field group. The schema dialog lists it as a rename; keep that choice to keep the values. Renamed and made shared in the same change, the field keeps the default language's value as its shared value, and the other languages go to the archive under the new name, so `nextly i18n:restore --field <new name>` brings them back once the field is translated again.

Two changes are refused alongside a rename, before anything is saved, and each works as two saves instead: changing how the field is stored (its length, its precision, or its type to a compatible one), and turning translation off for the whole collection, Single or field group. Rename the field and save, then make the other change. A change to an incompatible type is not a rename: the dialog lists it as removing one field and adding another.

A translated field renamed in code is not yet carried over: the old column keeps every language's value, and the new field starts empty. To rename one in code today, keep the old name until its values are moved.

## Fallback chains

`fallback: true` means a missing translation falls back rather than rendering empty. A
locale can name its own chain — `fallbackLocale: ["es", "en"]` tries Spanish, then
English. Without a chain, the default locale is used. A chain may pass through other languages but never back to the one it
starts from: a loop is refused when the configuration loads, and when the list is changed through
the API.

## Publishing one language at a time

Per-locale publishing needs **two** flags, not one. `localized` gives you translations;
`status` gives you the draft/published lifecycle. Only with both does each language get its
own state:

```ts
import { defineCollection, text } from "nextly/config";

export const Posts = defineCollection({
  slug: "posts",
  localized: true,
  status: true,
  fields: [text({ name: "title" })],
});
```

With both set, publishing the Spanish version does not publish the French one, and a language
still being translated stays invisible while the others are live.

<Callout type="warn">
  With `localized: true` alone you get translations and no lifecycle — there is
  nothing to publish per language, because the entity has no draft/published
  state at all.
</Callout>

<Callout type="warn">
  This is per-locale **publishing**, not per-locale scheduling. A [content
  release](/docs/releases) schedules the whole document across every language;
  it cannot schedule one language on its own.
</Callout>

## Access rules and languages

Every access rule — a collection's, a Single's and a field's — is told which languages it is
judging, so a rule can answer by language:

```ts
import { defineCollection, text } from "nextly/config";

export const Posts = defineCollection({
  slug: "posts",
  localized: true,
  access: {
    // The French translation is not open to editing yet.
    update: ({ permissions, locales }) =>
      permissions.includes("update-posts") && !locales.includes("fr"),
  },
  fields: [text({ name: "title" })],
});
```

- `locale` is the one language the operation is in: the language a read reads or a write
  writes. An unknown or missing `?locale=` is judged as the default it resolves to, and so is
  `*` on a read and `all` on a write, which each resolves the same way. A bulk create or update,
  and a duplicate, write the default language, and are judged in it.
- `locales` is every language the operation involves: `[locale]` for one language, followed,
  on a read, by each language a missing value falls back to (the site's fallback chain, or
  `?fallback-locale=`), since a value shown from a fallback is that language's content; and every
  configured language for a read of every translation (`locale=all`), a write to every language
  (`locale=*`), and an operation on the whole entry, such as a delete. There `locale` is absent.
  A duplicate copies what a read of the source shows in the default language, so its `locales`
  also lists each language that falls back to. A read that also reads each language's
  translation state (`?translation-status=1`, or a `_translated` filter) keeps its `locale` and
  lists every configured language, and so does an autosave that names a language the site
  doesn't configure. A collection or Single that isn't localized, and has no localized field
  group, stores the same content in every language, so an operation on it is told every
  language with no `locale`, whatever `?locale=` names.

A rule that limits someone to some languages should check `locales`, not only `locale`, so it
refuses an operation that reaches beyond them: a delete removes every language.

Write a language rule as a restriction, refusing when `locales` includes a language
(`!locales.includes("fr")`), not as an admission that allows when it does
(`locales.includes("fr")`). Where the languages an operation involves can't be known exactly,
such as an operation that names none or a collection built in the admin, the rule is told every
configured language. A restriction then refuses, which is safe; an admission by inclusion would
allow.

Publishing several languages at once — publishing every language of an entry or a Single, or
writing `status: "published"` with `locale: "*"` — asks the publish rule once for each language
it puts live, each time with `locale` set to that language and `locales` to all of them. A rule
such as `publish: ({ locale }) => locale !== "fr"` therefore refuses a publish that would put
French live, and since the publish is one transaction, no language goes live. A publish that
puts no French live is allowed.
