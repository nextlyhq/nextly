> **Alpha (`0.x`): pin your versions.**
>
> The stability boundary is `@nextlyhq/plugin-sdk` (see [API stability](/docs/plugins/stability)). This package's own exports, `seoPlugin`, its option types and the sitemap generators below, are **not** covered by that guarantee and are alpha. Pin your versions and read the release notes before upgrading.

The SEO plugin adds one field group to the collections and Singles you name, an SEO tab
that edits it on their pages in the admin, answers every page's head, and serves the
site's sitemap and robots.txt.

It is framework-agnostic and has no `next` dependency, so it works the same in an
integrated site, a headless project and an admin-only install.

**It does not render `<meta>` tags.** Turning the stored fields into Next.js `Metadata` is
core work, done by `buildMetadata` from `nextly/runtime`. The split is deliberate: the
plugin owns the data, and delivery belongs to whatever is serving the pages. See
[Routing and SEO](/docs/guides/routing-and-seo) for that half.

## Installation

```bash
npm install @nextlyhq/plugin-seo
```

Its peer dependencies are `nextly` and `@nextlyhq/plugin-sdk`, and while Nextly is in
alpha the manifest pins `nextly` at the **matching lockstep version**: every publishable
package ships on one train, so install the plugin and the core at the same version.

The plugin also declares a compatibility range for the runtime check: `>=` its own
version, so a core older than the plugin is refused at boot. Install the two at the same
version.

## Basic setup

```ts
import { defineConfig } from "nextly";
import { seoPlugin } from "@nextlyhq/plugin-seo";

export default defineConfig({
  plugins: [seoPlugin({ collections: ["pages", "posts"] })],
});
```

`collections` is the whole of the required configuration. Collections you do not name are
untouched.

## What lands on an entry

Every field goes inside a single group named `seo`, so entries always expose their SEO data
in one predictable place:

```ts
entry.seo?.metaTitle;
entry.seo?.metaDescription;
entry.seo?.socialTitle;
entry.seo?.socialDescription;
entry.seo?.ogImage;
entry.seo?.canonical;
entry.seo?.noindex;
```

**Each language has its own.** On a collection or Single whose content is translated, the
`seo` group is kept per language, as its translated fields are: a German title, description
or canonical never replaces the English one. On a type that is not translated, it holds one
value.

**Read the group defensively.** Adding the plugin to a collection that already has rows
adds a nullable column, and those existing rows carry `null` until they are next saved. A
bulk insert can omit it too, because that path does not apply nested defaults. So
`entry.seo` is optional even though every field inside it is. Core's own
`MetadataEntry` type declares it as `seo?: SeoMetaInput | null` for this reason.

### The default fields

| Field                | Type     | Notes                                                                                                                                                           |
| -------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `metaTitle`          | text     | Capped at 60 characters, which is roughly where search engines truncate a title                                                                                 |
| `metaDescription`    | textarea | Capped at 160 characters, for the same reason                                                                                                                   |
| `socialTitle`        | text     | The title a shared link's card uses, where it should differ from `metaTitle`                                                                                    |
| `socialDescription`  | textarea | The description a shared link's card uses, where it should differ from `metaDescription`                                                                        |
| `ogImage`            | upload   | Relates to `media`. The social preview image                                                                                                                    |
| `canonical`          | text     | A per-page canonical URL                                                                                                                                        |
| `canonicalElsewhere` | checkbox | Says the page first appeared on another site, so a `canonical` there is used                                                                                    |
| `noindex`            | checkbox | Defaults to `false`. Drops the entry from this plugin's sitemap. The `robots` directive that actually tells a crawler comes from `buildMetadata`, which is core |
| `structuredDataType` | text     | The [structured data type](#structured-data) this page is described as, where it differs from its content type's. Empty uses the content type's                 |

<Callout type="warn">
**Ticking `noindex` does not on its own keep a page out of search results.** The plugin
does two things with it, and one of them is nothing: the entry leaves this sitemap, and
that is all. A crawler that reaches the page by any other route still indexes it, because
the `robots` meta tag is emitted only if your app calls `buildMetadata` and renders what
it returns. An inbound link from another site, one of your own pages still linking to it,
and a URL already in an index are each enough.

That is the same split as everywhere else on this page: the plugin stores, core renders.
If you rely on `noindex`, make sure the pages for that collection actually render metadata
from `buildMetadata`.

</Callout>

All nine are optional. `canonical` and `noindex` ship by default rather than being left for
you to add, because a canonical URL and a search opt-out are baseline controls rather than
advanced ones.

### Custom fields

Replace the whole set when a project needs a different shape:

```ts
import { defineConfig } from "nextly";
import { text } from "@nextlyhq/plugin-sdk";
import { seoPlugin } from "@nextlyhq/plugin-seo";

export default defineConfig({
  plugins: [
    seoPlugin({
      collections: ["posts"],
      fields: [
        text({ name: "metaTitle", label: "Meta Title", maxLength: 60 }),
        text({ name: "focusKeyword", label: "Focus Keyword" }),
      ],
    }),
  ],
});
```

The field factories come from `@nextlyhq/plugin-sdk`, which is the stable
plugin-authoring surface and the type `fields` is declared against.

`fields` replaces the defaults rather than adding to them, so list everything you want.
Overrides stay nested under `seo`: the example above reads at `entry.seo.focusKeyword`.

## The SEO tab

On the edit page of every entry and Single the plugin adds the group to, while creating
one too, the admin draws an **SEO** tab after the page's own content. The `seo` group is
edited there, not among the page's fields, and the side panel holds none of it. What the
tab sets is part of the document: Save and Publish store it with everything else, so it
stays a draft until the page is published, as the page's other changes do.

The tab shows, in order:

- **A preview** of the page as Google lists it, and as the card a shared link shows on
  LinkedIn, Slack and others. It follows what is typed, saved or not, in any field of
  the page.
- **Title on Google** and **Description on Google**, with a count against what Google
  shows. An empty field shows, as its placeholder, the value the page will use, and under
  it where that value comes from: the content type's pattern, one of the page's own fields
  (its title, its excerpt), or the site's defaults. Typing marks it **Typed for this
  page**, with one action, **Go back to automatic**, that empties it again.
- **Advanced**, closed until opened: hiding the page from search, its official address
  (the canonical), a different title and description when shared, the share image, and
  the [structured data type](#structured-data), with what the type still lacks.
- **Check what search engines received**, once the page is saved and has an address: it
  opens [What search engines received](#what-search-engines-received) for this page.

The official address is the page's own public address. **Use another address** takes an
address on the same site as typed; one on another site is used only once the person
confirms the page first appeared there. Until then the page's own address stays in use.
"The same site" means one of its production addresses, scheme and port included. The row
is drawn only where the `seo` group has both `canonical` and `canonicalElsewhere`, since
an address on another site is used only once marked confirmed.

The count beside the tab's label is the number of problems the page's answer shows: a
title longer than Google shows, a description that is too long, a title or a
description that no level supplies, and each detail the page's structured data type
lacks. The title and description are checked by the same rule the
[problem list](#problems) uses, lengths counted in characters, so the tab and the list
always agree; a page hidden from search has no title or description problem in either.

The tab's values come from the same answer the page's head is built from, worked out by
the plugin's `POST /resolve` route for the document as it is typed. The route answers
anyone who may read that collection or Single, a reader shown the page read-only too.
What a page's route sets in its own code is not known to the admin, so the tab does not
show it.

The tab's component is `@nextlyhq/plugin-seo/admin#SeoTab`. `nextly generate:types`
adds it to your app's generated component map, as it does every component a plugin
declares.

The tab edits the fields the plugin ships, and offers a control only for the ones the
group declares. A `fields` option whose group has fields the tab
does not edit (a focus keyword, say), or a field it cannot honour as declared (read-only,
disabled, hidden or shown under a condition), keeps the whole group among the page's own fields
instead, where each one can still be edited, and no tab is drawn.

## The sitemap and robots.txt

The plugin serves the site's `/sitemap.xml` and `/robots.txt` at the root. `withNextly()`
rewrites both addresses to Nextly's API handler, where the plugin answers them, so there is
no route file to write. A site that ships its own `public/robots.txt`, `app/robots.ts`,
`public/sitemap.xml` or `app/sitemap.ts`, or rewrites one of them itself, keeps serving its
own: see [Answering a file at the site root](/docs/plugins/routes#answering-a-file-at-the-site-root).

### What the sitemap lists

Every published page of each content type that declares a public address, Singles
included, at that address. The homepage is listed like any other page: a Single or an entry
whose address is `/`.

Whether a page is listed is decided from the same answer its head is built from, so the two
never disagree. A page is listed when all of these hold:

- it is published. A working draft changes nothing listed until it is published;
- it is not hidden from search, on its own (`seo.noindex`) or with its whole type
  (`hiddenTypes`). Hiding it takes it out of the sitemap in the same change that serves it
  `noindex`;
- its canonical is its own address. A page whose canonical points to another page, on the
  site or off it, is that page's to list;
- the page holds its address. Where a deploy leaves two pages declaring one address, the
  page that held it keeps it, and the other is left out until it is given another.

A [page built in code](#pages-built-in-code) is listed too, once its route calls
`seoMetadata` and unless it is hidden from search: its head and its sitemap entry are then
built from the same answer.

A content type that declares no public address has no page in the sitemap, and nothing is
guessed for it. Declare one with `publicAddress` on the collection or Single:

```ts
import { defineCollection, defineConfig, text } from "nextly";
import { seoPlugin } from "@nextlyhq/plugin-seo";

export default defineConfig({
  collections: [
    defineCollection({
      slug: "posts",
      status: true,
      fields: [text({ name: "title" }), text({ name: "slug" })],
      publicAddress: "/blog/{slug}",
    }),
  ],
  plugins: [
    seoPlugin({ collections: ["posts"], baseUrl: "https://example.com" }),
  ],
});
```

On a site with several languages, each page is listed once in every language it is
published in, at the address that language serves it at, such as `/en/blog/hello` and
`/de/blog/hallo`, each with its [language links](#languages).

While the address record catches up at start, the sitemap answers `503` with
`Retry-After: 120` and `cache-control: no-store`, so no crawler or cache keeps a list that
leaves out pages whose addresses are not recorded yet.

Each entry carries:

- `<loc>`, the page's absolute address, made from `baseUrl`;
- on a page published in more than one language, an `<xhtml:link rel="alternate">` for
  each of its languages, itself included, and `x-default`, the same links as its head;
- `<lastmod>`, when the published page last changed. Saving a working draft leaves it as
  it was;
- the page's main image as an `<image:image>`: its share image, or the cover image its
  content offers, as the page's head uses it. The site's default share image, which every
  page shares, is not listed.

**Large sites get a sitemap index.** One file holds at most 50,000 addresses and 50 MB.
Past either, `/sitemap.xml` answers a sitemap index naming each file as
`/sitemap.xml?page=1`, `/sitemap.xml?page=2` and so on. `sitemap.maxUrlsPerFile` and
`sitemap.maxBytesPerFile` make the files smaller; they never make them larger than the
protocol allows.

<Callout type="warn">
**The sitemap is public and reads as the system.** It lists every published page's address
in the types it covers, bypassing per-collection read access. Declaring a public address
states that a type's pages are public. To keep a type's pages out, hide the type
(`hiddenTypes`), or list only some collections with `sitemap: { collections: [...] }`.

It is built from the database on every request. Set `baseUrl` so the answer can be cached,
and cache `/sitemap.xml` in front of the site on a large one.

</Callout>

### Hiding a whole type

`hiddenTypes` hides every page of a content type from search, such as tag or author
listing pages. Each is served `noindex` and left out of the sitemap, whatever the page's own
setting. Remove the type from the list and each page returns to its own setting.

```ts
import { defineConfig } from "nextly";
import { seoPlugin } from "@nextlyhq/plugin-seo";

export default defineConfig({
  plugins: [
    seoPlugin({
      collections: ["posts", "tags"],
      hiddenTypes: ["tags"],
    }),
  ],
});
```

A Single is named `single:<slug>`.

### robots.txt and AI crawlers

`/robots.txt` lets search engines read every page but the admin and the API, the same paths
`nextlyRobots` keeps out (both read `FRAMEWORK_CRAWL_EXCLUSIONS` from `nextly`), and names
the sitemap by its absolute address:

```txt
User-agent: *
Allow: /
Disallow: /admin/
Disallow: /admin$
Disallow: /admin?
Disallow: /api/
Disallow: /api$
Disallow: /api?

Sitemap: https://example.com/sitemap.xml
```

`aiCrawlers` decides what AI tools are asked:

| Choice     | What it asks                                                                                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"all"`    | Nothing: every AI tool may read your pages, for AI search answers and for training. The default                                                                                        |
| `"search"` | Tools that collect pages to train AI models, such as `GPTBot`, `ClaudeBot`, `CCBot` and `Google-Extended`, are asked not to. Tools that answer questions may still read and cite pages |
| `"block"`  | Every known AI tool is asked to stay away                                                                                                                                              |

These are requests. Well-behaved tools follow them; some ignore them. Asking Google not to
use your pages for AI training (`Google-Extended`) also limits what Gemini can use from
them. Google Search and Bing are not affected by any choice.

### The site's address, and why it affects caching

Both files name the site by one of its production addresses, read as the page's head reads
them: `NEXTLY_PRODUCTION_ADDRESSES` first, the one a request reached where it is among them.
Without one, `baseUrl` is used: an absolute `http(s)` origin with no path, query, fragment
or credentials. An invalid value throws when the plugin is constructed, so a typo fails at
boot. A page whose canonical is on another of the site's addresses is listed in that
address's sitemap.

Without either, each request's own origin is used. That is right for a single-origin deployment,
and wrong behind a proxy that rewrites the host. Because a request's host is whatever its
sender says, both files are then served with `cache-control: no-store`, so nothing in front
caches one host's answer and serves it for another. **Set `baseUrl` for a cacheable sitemap.**

### Reading the listed pages

Other code can read what the sitemap lists, and the pages left out because another page
holds their address, through the plugin's `listedPages` service. Its `list(origin)` answers
`{ pages, problems }`. Each page and each problem names its `language`, and a page published
in more than one language carries its language links as `alternates`.

### Before the sitemap reached the root

The sitemap is still served at its earlier address,
`/admin/api/plugins/@nextlyhq/plugin-seo/sitemap.xml`, with the same pages. Where it is an
index, the files it names are at that same address (`?page=<n>`), so it works without the
root rewrite.

`urlFor` and `basePath` no longer shape it. A sitemap that guessed a page's address could
name one the page is not served at, and disagree with the page's own canonical. The plugin
logs a warning at start while either is set. Declare `publicAddress` on each public type
instead.

`generateSitemap`, `buildSitemapUrls`, `serializeSitemap`, `defaultUrlForEntry` and
`escapeXml` are still exported and still read `urlFor` and `basePath`, for a project that
builds a sitemap from its own route. They are deprecated, and list pages by the old rules:
they do not read each page's answer.

## Search Console and IndexNow

Two optional connections on **SEO > Settings > Connections**. Neither is on until someone
who may manage site-wide SEO turns it on, and if one fails, the Connections tab and the
problem list say so in plain words and no page is affected.

### Google Search Console

Search Console shows the site's clicks from Google over the last 28 days, what people
searched, and the pages where Google chose a different official address than the page
names (of the most visited ten, checked with Google's URL inspection). Connecting it needs a
Google sign-in for the site: create an OAuth client of the **Web application** kind in Google
Cloud, add the redirect address below, and name it in the plugin's options, keeping the
secret out of the code:

```ts
import { secret } from "@nextlyhq/plugin-sdk";
import { seoPlugin } from "@nextlyhq/plugin-seo";

seoPlugin({
  collections: ["posts"],
  searchConsole: {
    clientId: process.env.GOOGLE_CLIENT_ID ?? "",
    clientSecret: secret(process.env.GOOGLE_CLIENT_SECRET ?? ""),
  },
});
```

The redirect address is the admin's own, on each host people sign in to the admin on:
`https://<host>/admin/api/plugins/@nextlyhq/plugin-seo/connections/search-console/callback`.

**Connect Search Console** sends the person to Google, which asks them to approve read-only
access (`webmasters.readonly`, with `openid email` to show who connected). Nextly never
changes anything in Search Console. The property used is the one for the site's production
address: its URL-prefix property, else its domain property. The token that renews access is
kept encrypted in the plugin's settings, with the sign-in's one-time state and PKCE verifier
while it is under way; none of them is ever returned to the admin or any API, or logged.
**Disconnect** withdraws the access at Google and forgets it.

### IndexNow

IndexNow tells Bing and the other search engines taking part the moment a page is published,
changed, given a new address or taken down. Google does not take part. Changes are gathered
for a few seconds after the last save, so a burst of saves makes one notice, and sent after
the save has finished: a save never waits for IndexNow, and a working draft's save sends
nothing.

The site proves it owns its pages with a key served at its root, `/<key>.txt`, answered by the
site's [Proxy](/docs/plugins/proxy) while IndexNow is on. The key is made the first time a
notice is sent and kept encrypted in the plugin's settings. Every notice goes to
`api.indexnow.org` only. A refused key (`403` or `422`), a rate limit (`429`) or an endpoint
that cannot be reached is shown on the Connections tab and listed on the problem list until a
later notice goes through; the next change is sent again. Notices name the site's production
address, so IndexNow needs one saved.

The plugin may reach only `api.indexnow.org`, `oauth2.googleapis.com`, `www.googleapis.com`
and `searchconsole.googleapis.com`, each request given ten seconds and following no redirect.

## llms.txt and plain-text copies

Two optional outputs for AI tools, both off until someone switches them on in **SEO >
Settings > Connections**. Few tools read them today, so neither is on by default.

- **`/llms.txt`** is a plain list of the site's pages, in the format the
  [llms.txt proposal](https://llmstxt.org) sets out: the site's name as the heading, its
  default description beneath it, and each page as a link under its content type, with the
  title and description its head carries, worked out from what the public may read of the
  page; a page the public may not read is listed by its address alone. It lists exactly the pages the sitemap lists, by
  the same rules, so a draft, a hidden page or a page whose canonical points elsewhere is
  never in it. Until it is switched on, `/llms.txt` is not found. Like the sitemap, it
  answers `503` while the address record catches up at start.
- **Plain-text copies** add a text version of each page the sitemap lists, at the page's
  address with `.md` added: `/blog/hello.md` for `/blog/hello`, and `/index.html.md` for
  the home page. The copy is the page's title as a heading, then the words of its text,
  long text and rich text fields, in the order its type declares them, those inside its
  groups and repeaters included, with rich text's headings, lists, links, quotes, code,
  tables and images written as Markdown. A field group's rich text is read too. A page's SEO
  fields, its address, fields holding a choice, a number or a date, and other documents
  read with it, such as an author, are left out. Each copy is served as
  `text/markdown; charset=utf-8` and names its page as canonical in a `Link` header, so
  search engines keep listing the page. With copies on, `/llms.txt` links each page's copy.

A copy is read as a visitor with no session reads the page: the Public role's grants, the
type's read rule and each field's read rule decide what is in it, so a field kept from the
public is never in a copy, and a page the public may not read has none. Where a page of the
site already has a copy's address, such as a page at `/guide.md`, that page is served there
and no copy is, and `/llms.txt` links the page itself. A page at `/index.html` keeps
`/index.html.md`, and the home page is then linked as itself. A copy's words are escaped
where Markdown would read them as markup, so it says what the page shows.

Every reader gets the same answer: neither output looks at who is asking. Neither changes a
page either: llms.txt is its own file, and a copy is answered only at a copy's address. A
copy is answered by the site's [Proxy](/docs/plugins/proxy), so the site needs its
`proxy.ts`, as [redirects](#redirects) do; a site that ships its own `public/llms.txt` or
`app/llms.txt/route.ts` keeps serving it.

A copy is made from the page as it is stored, the fields the site renders, not from the
rendered page: the words of a Page Builder layout are not in it.

## Languages

On a site with [several languages](/docs/localization), each page's head links to the page in
every other language it is published in, and the sitemap lists the same links:

```html
<link rel="canonical" href="/de/ueber" />
<link rel="alternate" hreflang="en" href="/en/about" />
<link rel="alternate" hreflang="de" href="/de/ueber" />
<link rel="alternate" hreflang="x-default" href="/en/about" />
```

- **Only where the page is published.** A language the page has no published version in is
  not linked: one it was never translated into, where each language is published on its
  own, or one whose translation is still a draft. Publishing the translation adds the link to
  every version of the page, and withdrawing it takes it away.
- **Every version names every other, itself included,** each at that version's own canonical,
  formed by the site's [language rule](/docs/localization#each-languages-address): under a
  prefix, or on the language's own domain. A version hidden from search, or one whose
  canonical names another page, is linked from none, and a page in one language has no
  links at all.
- **`x-default`** names the site's default language's version, where the page is published
  in it.
- **Codes search engines accept.** A link names a language by its ISO 639-1 code, with an
  ISO 15924 script and an ISO 3166-1 region where the site's language has one, such as `de`,
  `pt-BR` or `zh-Hant-TW`. A language spelled another way is mapped: `pt_BR` to `pt-BR`,
  `deu` to `de`, `en-UK` to `en-GB`. One with no such code, such as `es-419`, is left out of
  every link, and so is a second language that maps to a code another already has.

On a site whose languages are on their own domains, each domain's sitemap lists its own
language's pages, with links to the others on theirs.

Other code can read a page's links, and the languages left out for their code, with
`pageLanguageLinks(ctx, input)`, and check a language with `hreflangOf(code)`.

## The SEO settings

The plugin adds an **SEO** item to the admin's rail. Its **Settings** page holds the rules for the
whole site; a page's own values always win over them.

The first time someone opens it, three short questions come first: the site's name and production
address, what kind of site it is and what AI tools may do, and a logo with a default share image.
Each answer is saved as they move on, and closing the questions part-way keeps what was answered,
with a line on the page to finish later. Every answer stays editable on the tabs:

| Tab           | What it holds                                                                                                                                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| General       | The site's name, its production address (one per domain where a language has its own), the separator between a title and the site's name, the default share image and description                                                               |
| Content types | Each content type with SEO (set in code), whether it has a public address yet, its title pattern, whether the whole type is hidden from search, and what its pages are described as in structured data, with the field each detail is read from |
| Brand         | The kind of site, the brand's name and other names, its logo, and its social profiles                                                                                                                                                           |
| Crawlers      | What AI tools are asked to do with the site's pages: allowed (the default), search but not training, or none                                                                                                                                    |
| Connections   | Optional services and outputs, each off until switched on: [Search Console and IndexNow](#search-console-and-indexnow), [llms.txt and plain-text copies](#llmstxt-and-plain-text-copies)                                                        |

The production addresses saved on General are the ones the page's canonical, the sitemap,
robots.txt and the staging guard all read; `NEXTLY_PRODUCTION_ADDRESSES`, where it is set, wins over
them for all of them. The AI tools choice on Crawlers is what robots.txt asks, and content types the
settings hide are hidden from every output; until the site chooses, the plugin's `aiCrawlers` and
`hiddenTypes` options answer.

Opening the page needs `manage-seo` and `read-seo-settings`, and saving needs `manage-seo` and
`update-seo-settings`. The last two are seeded with the plugin's `seo-settings` Single, which holds
the settings, and the Single answers no one without `manage-seo`, however it is asked. See
[Who may change SEO](#who-may-change-seo).

### Title patterns

A content type's titles are made from its pattern wherever a page has no title typed. Every type
starts with `{Title} | {Site name}`, using the separator chosen on General. Click a pattern to
change it: the variables the type offers can be clicked in, and an example title from the type's
newest page updates as you type.

- `{Title}` is the page's own title, `{Site name}` the site's name, and any other variable one of
  the type's own text or number fields, such as `{Category}`.
- A pattern naming a variable the type has no field for is refused before it can be saved.
- A pattern whose variables a page has no value for gives way to the next source in the order
  below, rather than leaving a gap in the title.
- The site's name is never added right after a title that already ends with it: with the pattern
  `{Title} | {Site name}`, a title typed as `Pricing | Acme` stays `Pricing | Acme`.

**Reset to default** returns a type to the site's default pattern.

### Hiding a type, and its structured data

The table lists every content type the plugin adds SEO to, with one entry's address as an example
of where its pages live, and after them, greyed, the site's other types: SEO is switched on or off
for a type in the site's code, so the switch there can't be changed.

**Hide whole group** keeps every page of a content type out of search, whatever each page says, and
out of the sitemap. The **Structured data** column chooses what the type's pages are described as;
**Automatic** describes a page with an author and a date as an Article, and any other as a Web page.
For a type that needs details, such as an Article's author, **Map details** chooses the field each
detail is read from, including a field inside a group (`event.startsAt`), and the optional details
the type can also use. A detail left unchosen is read from a field named like it, the image from the
page's share image, and a type missing a detail is left out of the page's markup and listed in
Problems.

Until the site chooses, the table shows what the plugin's `hiddenTypes` and `structuredData` options
say. Hiding or showing a type saves the whole list, which then takes over from `hiddenTypes`. A
type's structured data choice takes over from the option for that type only; other types keep
following the option, and choosing **Automatic** over a type the option names is kept as a choice.

### Changes reach pages without a redeploy

Every save of the settings expires the cached heads built from them, so the next request for any
page reads the new rules. The settings are one set for every language of a translated site.

### Reading the settings in code

```ts
import { definePlugin, respondDoc } from "@nextlyhq/plugin-sdk";
import { readBrandFacts, readSeoRules } from "@nextlyhq/plugin-seo";

export const brandCard = definePlugin({
  name: "@acme/brand-card",
  version: "1.0.0",
  nextly: ">=0.0.2-alpha.74",
  contributes: {
    routes: [
      {
        method: "GET",
        path: "/brand",
        public: true,
        handler: async (_req, ctx) => {
          const rules = await readSeoRules(ctx);
          const brand = await readBrandFacts(ctx);
          return respondDoc({ site: rules.siteName, profiles: brand.profiles });
        },
      },
    ],
  },
});
```

Read them while handling a request or a job, never while the site starts: they wait for the start
to finish, so awaiting one in a plugin's `init` or `onReady` would wait on itself.

`readSeoRules` answers the site's name, default description and share image, production addresses,
the default pattern and each type's own patterns. `readBrandFacts` answers the brand's names, logo,
social profiles and kind of site. Each reads the settings once; a read cached by your own code
should carry `seoSettingsCacheTags()`, which every save expires.

## Turning the fields into tags

With the plugin installed, every page served by a content route or a Single route gets its head
from the plugin: nothing to call in `generateMetadata`. Each value is worked out on its own, from
the first of these that has one:

| Order | Where the value comes from                                                     | For                                         |
| ----- | ------------------------------------------------------------------------------ | ------------------------------------------- |
| 1     | What a person typed in the page's `seo` group                                  | every value                                 |
| 2     | What the route's own `buildMetadata` returns                                   | title, description and the social card only |
| 3     | The Page Builder design drawing the page                                       | title, description, the social card         |
| 4     | The content type's pattern, such as `{Title} \| {Site name}`                   | title, description                          |
| 5     | The page's own content: its `title`, `excerpt` or `summary`, and a cover image | title, description, share image             |
| 6     | The site's defaults                                                            | title, description, share image             |

Level 3 is what the design drawing the page sets: a page's own blocks, or the template or own
design an entry is drawn with, its SEO settings first. A route hands it as it serves the page; the
SEO tab, the problem list and the check of what search engines received ask the Page Builder for
it, where it is installed, so they show the value the page is served with.

A level with nothing for a value, or only blank text, gives way to the next, so a page is never
served an empty title. A pattern whose tokens have no value gives way too, rather than leaving a
gap. What a person typed always wins, so a route's code fills only what nobody typed.

- **Visibility** is never code's to decide: a page is listed unless `noindex` is set on it.
- **The canonical** is the page's own declared address, in the language it was read in, formed by
  the site's [language rule](/docs/localization#each-languages-address). A page whose type
  declares no address gets no canonical rather than a guessed one, and so does a page whose
  address another page holds: it lost the address in a clash, and gets one back when it is given a
  new address. A canonical typed in the `seo` group overrides it only where search engines can
  follow it (a path from the site's root, or an `http(s)` address) and only on the site's own
  production addresses, unless `canonicalElsewhere` says the page first appeared on another site.
- **The share image** may be stored as a media id: the plugin looks it up, so a page read at
  `depth: 0` keeps its image.

## Keeping copies out of search

A preview, a staging copy or a production build served from another host must never compete with
the real site. With the plugin installed, the site's Proxy sends `X-Robots-Tag: noindex` with
every response from any host but the site's production addresses, prerendered pages included.
Wire the Proxy once, in `proxy.ts`, as [Proxy handlers](/docs/plugins/proxy) shows.

Name the production addresses in the environment, as bare origins, comma-separated:

```bash
NEXTLY_PRODUCTION_ADDRESSES=https://example.com,https://example.de
```

The environment wins over the SEO settings, so a deploy can't be indexed by mistake while its
settings are being changed. With no address known, the plugin decides once, the first time it
starts on a site:

- **A site with no pages yet** is kept out of search everywhere until it has an address.
- **A site that already has pages** stays listable, and its missing address is listed as a
  problem to fix. Dropping a live site out of search is the worse error.

Without the plugin, `buildMetadata` from `nextly/runtime` still turns the `seo` group into a
Next.js `Metadata` object by hand. The `buildMetadata` section of
[Routing and SEO](/docs/guides/routing-and-seo) covers it.

## Social cards

When someone shares a page on LinkedIn, X, Slack, Facebook or WhatsApp, the network shows a card
built from the page's head. The plugin states everything the card reads:

- the title and description, the social ones where a page has them, else the page's own;
- the **share image** at its full address, with its width, height and alt text. The media library
  stores an upload with a path from the site's root (`/uploads/cover.jpg`), which a network cannot
  load, so the plugin states it on the site's production address (the page's language's own, where
  it has one on its own domain), else `baseUrl`, else the origin of the page's canonical where that
  is absolute;
- the **site's name**, the one saved on the SEO settings' General tab, so the card, the title
  pattern and structured data name the site the same way; until it is saved, `socialCard.siteName`;
- the page's **language**: the one the route read it in, or else `socialCard.language`, or else
  the site's default language (English on a site that declares no languages), written as Open
  Graph writes it (`en-US` becomes `en_US`).

```ts
seoPlugin({
  collections: ["posts"],
  baseUrl: "https://example.com",
  socialCard: { siteName: "Acme", language: "en-US" },
});
```

The image's alt text is the media item's own, so give share images alt text in the media library.

### Share images of the right size

Networks show a share image in full at 1200 × 630. A picture narrower than 1200 pixels, or whose
width is not between 1.8 and 2.0 times its height, is cropped or shrunk. `shareImageProblems(ctx,
input)` says so for a page, such as `800 × 600, LinkedIn will crop it`, and says where it is fixed:
by making a share image, in the route's code where the route set the picture, or in the settings
where the site's address is missing. `shareImageSizeProblem({ width, height })` answers the same
for one picture.

Making a share image is one action. The plugin's `POST /share-image` route
(`/admin/api/plugins/@nextlyhq/plugin-seo/share-image` in a scaffolded project), sent
`{ "media": "<media id>" }`, makes a copy of the picture at exactly 1200 × 630, cut around the
picture's focal point and enlarged where it is smaller, as a JPEG under 600 KB. It adds the copy to
the media library, in the same folder and with the same alt text, and answers it as
`{ message, item }`; set the item as the page's `seo.ogImage` to use it. The picture itself, and every page that shows it, are unchanged.

The route is for a signed-in person who may add to the media library (`create-media`) and read it
(`read-media`). It reads the picture from where the site serves its uploads, on `baseUrl` where it
is set. A picture that storage will not serve to an anonymous reader is refused, since no network
could load it either. It needs the `sharp` image library, which the media library uses to read image sizes:
install it with `npm install sharp`.

In the SEO tab, the **When shared** preview says how the share image fits the card: the size every
network shows in full, or where a picture of another shape is cut, with a dashed line where the card
cuts a taller one. Under **Advanced**, a share image of the wrong size offers **Make a share image**.
Once made, the copy is the page's share image, the row says **Made for this page** and what it was
made from, and **Go back to automatic** returns to the page's own picture.

## Structured data

Each page served by a route helper also gets structured data: JSON-LD describing the site, the page
and what the page is about, which search engines read to show details such as an article's author
and date, or a product's price. It is built from the same answer as the page's head, so its title,
description, address and image are the head's own. Every address in it is absolute, so it needs the
site's origin: set `baseUrl`.

A page is described as one linked graph:

- the **organisation** that owns the site (`structuredData.brand`: its name, logo and official
  profiles), and the **website**, named by the site name;
- the **page**, at its canonical address, with a **breadcrumb trail** from the site's home;
- the page's **subject**, as its type describes it.

Only types Google still shows a result for are offered:

| Type            | Key                   | Details it needs                              |
| --------------- | --------------------- | --------------------------------------------- |
| Article         | `article`             | author, date published, image                 |
| Blog post       | `blogPosting`         | author, date published, image                 |
| Web page        | `webPage`             | none                                          |
| Collection page | `collectionPage`      | none                                          |
| Profile page    | `profilePage`         | person                                        |
| Software app    | `softwareApplication` | operating system, price, rating, rating count |
| Product         | `product`             | price, availability                           |
| Event           | `event`               | start date, location                          |
| Video           | `videoObject`         | video file, upload date, image                |
| Review          | `review`              | author, item reviewed, item type, rating      |
| Local business  | `localBusiness`       | street address, opening hours                 |

The image is the page's share image unless a field is mapped to it. A rating is read out of 5, as
search engines read one with no scale; a content type rating out of 10 maps `bestRating`, such as
`{ value: "10" }`, and a rating off its scale is reported missing. An event's location is a group or
an entry with the venue's name and its address, never text alone. A page with no type chosen is
an Article when it has an author and a publish date, and a Web page otherwise. A content type
chooses its pages' type, and a page can choose another in its `seo.structuredDataType`. A page
hidden from search is offered only Web page and Collection page.

Each detail is read from the field the content type maps to it, or else from the first field named
like it (`author`, `publishedAt`, `price`, `startDate` and so on). Structured data states only what the route
read for the page, so a relationship names someone only where the route read the entry it holds:
give a route that shows its author `depth: 1`. The route's own access rules, language and cache
tags then govern the author as they govern the page, so an unpublished or private author is never
named. An author with a public address of their own is linked to it. A relationship read at
`depth: 0` holds only an id, which is not a name, and the problem says the route is the fix.

```ts
seoPlugin({
  collections: ["posts", "events"],
  baseUrl: "https://example.com",
  structuredData: {
    brand: { name: "Acme", profiles: [{ url: "https://x.com/acme" }] },
    types: {
      posts: { type: "blogPosting" },
      events: {
        type: "event",
        // A field by name, a field in a group, or a value for every page.
        // A group holding the venue's name and its address.
        details: { event: { startDate: "startsAt", location: "venue" } },
      },
    },
  },
});
```

The [SEO settings](#the-seo-settings) take over from these options fact by fact: their first
production address is the origin, their brand name (else the site's name), other names, logo and
social profiles describe the organisation, and a content type's choice kept in the settings wins
over the one given here. Whatever the settings leave empty, the options still answer.

**A type missing a detail it needs is left out**, rather than sending search engines a description
they would reject; the page and the site are still described. `structuredDataProblems(ctx, input)`
lists one problem per missing detail, such as `Missing: author.`, saying whether the page's field is
empty, no field holds it yet, or the route read its relationship without the entry. A page with no canonical address is given no guessed one: only the
site is described.

The route helpers hand the page's render the structured data as `context.structuredData`, text
written so that no value can end its script element. Place it in the page, so it is in the HTML a
crawler receives:

```tsx
{
  context.structuredData && (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: context.structuredData }}
    />
  );
}
```

Page Builder routes (`createBlocksPage`, `createSinglePage`, `createContentPage` and their public
forms) place it themselves, before the page's blocks, so a page built in the Page Builder needs
nothing more.

## Redirects

A published page whose address changes leaves a permanent redirect from its old address to its new one, with no question asked: rename a post's slug from `hello` to `hello-world` and `/hello` goes on sending people, and search engines, to `/hello-world`. A deploy that changes an address template does the same, at the next start.

- **One hop.** A redirect is stored to the end of its chain: move a page from `/a` to `/b` and then to `/c`, and `/a` and `/b` both go straight to `/c`.
- **No loops.** A redirect that would come back to where it started is refused. Moving a page back to an old address takes that address from its redirect, since the page is meant to live there.
- **None where another page lives.** No redirect is made from an address another page holds after the change, so two pages swapping addresses make none, and a page taken off the site leaves none.
- **Kept, or refused.** If a save's redirect cannot be stored, the save is refused with the reason and the page keeps its old address. After a deploy the route has already moved, so the old address is listed among the addresses not found instead.

A redirect's From address is held like a page's address, so a published page and a redirect never share one. A From address may also be a pattern, `/old/*`, sending `/old/anything` to the same place under a new address with a To address of `/new/*`. Where several redirects match, an exact one answers first, then the pattern with the longest fixed part. A page at an address inside a pattern is served, and the pattern still redirects every other address below it.

### The redirects screen

**SEO › Redirects** in the admin lists every redirect, who added it and when. Add one by typing its From and To addresses as visitors open them (`/old-page`, or `/de/alt` on a site with language prefixes), with a pattern such as `/old/*` to `/new/*` for a whole section. A To address may also be a full `https://` address on another site. A redirect is permanent unless you choose Temporary, which tells search engines the page is coming back.

The form refuses what would break: an address a published page holds, a second redirect from one address, and a redirect that would send visitors round in a loop. Where the To address already redirects onward, the new redirect goes straight to the end in one hop, and the form says so.

The **Not found** tab lists the addresses people and search engines asked for that don't exist, most visited first. **Redirect…** fills the form with the address and the closest live page as a suggestion, for you to check before adding.

The screen, its import and the **Not found** tab are for someone holding `manage-seo`. The plugin keeps the redirects and the not-found log itself, so the permissions the role screen lists for their collections open nothing on their own.

### Importing redirects from a file

**Import CSV** reads a file of redirects, one per line: the From address, the To address and, optionally, `temporary`. A first line naming the columns is skipped.

```text
From,To,Type
/old-blog/*,/blog/*
/guides/seo-basics,/resources
/webinar,/events/spring-webinar,temporary
```

Nothing changes until you confirm. The dry run shows what each row would do: a new redirect, one that joins a chain or replaces an existing redirect, one already there, or one that can't be imported, such as a loop. A file with any row that can't be imported is not imported at all; fix it and upload it again. A confirmed file is applied in full or not at all.

### Running redirects

Redirects answer from the site's Proxy, before the page is served, so a page that no longer exists never starts streaming a "not found" first. Wire the Proxy once, as [Proxy handlers](/docs/plugins/proxy) shows:

```ts
// src/proxy.ts
import { createNextlyProxy } from "nextly/runtime";

import nextlyConfig from "../nextly.config";

export const proxy = createNextlyProxy(nextlyConfig);

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

A saved redirect applies from the next request, on every server, since each request reads it. A permanent redirect answers `301`, a temporary one `302`, and the visitor's query string goes with them unless the To address has its own. Admin, API and asset requests are never redirected.

### Addresses not found

The plugin keeps a log of the page addresses people and search engines asked for that did not exist, one row per address with how often and when, so each can be given a redirect. Admin, API and asset requests are left out, and the log keeps its most recent and most frequent addresses once it reaches 1,000.

Log a request from the site's not-found page, with the request headers the Proxy passes on:

```tsx
// src/app/not-found.tsx
import { logNotFound } from "@nextlyhq/plugin-seo";
import { headers } from "next/headers";
import { connection } from "next/server";
import { Suspense } from "react";

async function LogThisAddress() {
  await connection();
  await logNotFound(await headers());
  return null;
}

export default function NotFound() {
  return (
    <main>
      <h1>Page not found</h1>
      <Suspense fallback={null}>
        <LogThisAddress />
      </Suspense>
    </main>
  );
}
```

The log is written under a `Suspense` boundary because reading the request's headers makes that part dynamic, which Cache Components requires to sit inside one. `connection()` keeps a prerender of the page from logging anything: only a visitor's request is counted.

A request is counted once, however many times Next.js renders its not-found page. `logNotFound` never throws, and logs nothing for a request the Proxy did not pass on.

## Problems

**SEO › Problems** in the admin lists what affects how the site shows up in search and when
shared, grouped by kind, each with a button that goes straight to its fix: the page's SEO tab or
its content, the SEO settings, the media library, or a note to copy for a developer where the fix
is in code. There is no score, and nothing on the list stops anyone publishing.

Each public page of the collections and Singles the plugin extends is checked, in every language
it is published in and at its address there, as its head would be served, for:

- no title or description from any level (a field left empty is never reported where a pattern,
  the page's content or the site's defaults supply a value);
- a title or description another page has too;
- a title over 60 characters, or a description over 160;
- a canonical typed for the page that names another address;
- a link in its content to an address of a content type that no page holds;
- no share image, or one networks crop or shrink;
- an image in its content (rich text, a media field or a Page Builder image block) with no alt
  text, unless it is marked decorative;
- structured data missing a detail its type needs;
- a language the site's language links leave out, because search engines don't accept its code.

A page hidden from search on purpose is checked only for broken links and alt text. The site as a
whole is checked for a missing production address, a collection with no public address, a
redirect whose To address redirects again, and a page left out of the sitemap because another page
holds its address.

The list is for anyone who may read one of the content types the plugin extends, a Single among
them, and shows each person the problems of the pages they may read. A redirect that takes more
than one hop is listed only for someone holding `manage-seo`, who may see the redirects.

### On the dashboard

The **SEO issues** card draws the list by kind, one bar for each kind of problem, and the
**Needs attention** card has one **SEO problems** line counting the whole list, linked to it. Both
read the list the person looking may read, from the same kept results, so their numbers are the
list's. The card is offered to someone who may read every collection the plugin extends, the line
to someone who may read one of them. A dashboard card can't ask for `manage-seo`, so neither counts
a redirect that takes more than one hop: those are on the list itself.

### When the list is checked

- **A page is checked again when it is saved**, after the save, so a check never slows or undoes
  it. A save that changes a page's address, title or description, and a deletion, mark the last
  full check as out of date, since another page's result may have changed.
- **The whole site is checked when the list opens** and its last full check is over 24 hours old,
  and whenever someone chooses **Check now**. The list says when it was last checked. No scheduler
  is needed, so this works the same on a self-hosted server.
- **Serving a page runs no check.** What each check found is kept, and the list reads it.
- **A full check waits for the plugin's record of addresses** to be brought up to date after a
  start; until then the list asks to check again in a minute, as the sitemap asks crawlers.

The list answers each person with the pages they may read, and names a collection only to its
readers. It is served at
`/admin/api/plugins/@nextlyhq/plugin-seo/problems`, and a full check at
`/admin/api/plugins/@nextlyhq/plugin-seo/problems/check` (`POST`), for a signed-in person.

The check reads the values the plugin keeps: the page's own, its content type's pattern, its
content and the site's defaults, and, where the Page Builder is installed, what the design drawing
the page sets, worked out as the page's route works it out. A title, description or share image
that only the route's code sets is not seen, so such a page is listed as missing it; typing the
value on the page's SEO tab settles it either way.

Not checked yet: whether a response is small enough for every value to fall within its first
2 MB, and whether a page built in code calls the plugin's metadata function. Both need the page
fetched as a search engine fetches it. A link is judged only under a collection's own address
prefix (`/blog/{slug}`): under one served from the root (`/{slug}`), pages built in code share
every address, so a missing one can't be told from the record alone.

## What search engines received

The **What search engines received** screen, under SEO in the admin, fetches one of the
site's pages as Googlebot, LinkedIn, X and Slack would, and shows what each received beside
what Nextly holds for the page: its title, description, share image, official address
(canonical) and whether it is listed in search. A value that differs is numbered in the
table and explained below it in plain words, with its likely cause: a copy the host saved
before the last change, a title template in the site's layout, an `opengraph-image` file
beside the route, a `noindex` sent in a header, or a firewall that turned a crawler away.
Where LinkedIn received something different, the explanation links its Post Inspector,
which refreshes the card LinkedIn keeps for about a week.

Open it from a page's SEO tab, which names the page at the address its language serves it at
(with the language in it, on a site that puts the language in every address), or from the menu,
where it checks the site's first listed page. Any address on the site can be typed in. What Nextly holds is the head the plugin
answers for the published page at that address, shown only to someone who may read that
page's content type. Running a check, and the screen itself, need `check-seo`, since a check has
the server fetch the site's pages.

What Google shows in its results can still differ from what Googlebot received: Google
sometimes writes its own title, and keeps an older copy until it visits again. The check
shows what the page serves today.

### Which addresses can be checked

The check makes your server fetch a page, so it fetches only the site's own pages, and
refuses, before anything is fetched, an address that:

- is not on one of the site's production addresses (`NEXTLY_PRODUCTION_ADDRESSES`, else
  the production address in the SEO settings) or the plugin's `baseUrl`;
- uses a port other than 80 or 443, unless it is exactly the port a production address
  names;
- carries a user name or password; or
- resolves to an address inside a private network, on this machine, or link-local
  (where cloud metadata services answer). A production address set on this machine by
  number or as `localhost`, such as `http://localhost:3000`, may be checked there, at
  exactly that address.

Every redirect is held to the same rules before it is followed, and the connection is
made to the very address that was checked, so a name whose answer changes in between
reaches nothing new. A fetch stops after 10 seconds, 5 MB or 5 redirects, and says so.
With no production address set, the screen asks for one and checks nothing.

| `manage-seo`      | Site-wide SEO: the [SEO settings](#the-seo-settings) (with the Single's own read or update permission beside it), [redirects](#redirects), their imports, the addresses not found, and the SEO of [pages built in code](#pages-built-in-code) |
| `check-seo`       | [What search engines received](#what-search-engines-received): the screen, and the check it runs                                                                                                                                              |
| `edit-seo-<type>` | Changing the SEO of one content type's pages, such as `edit-seo-posts`, where `pagePermissions` is on                                                                                                                                         |

Each is asked by the server on every request, whatever the admin shows: someone without it is
refused and given nothing of what it guards. The admin hides the Pages and addresses, Settings, Redirects and What search
engines received entries from someone without the screen's permission.

A page's SEO is part of the page. By default whoever may edit a page changes its SEO, and an SEO
change is saved like any other change to it: held as a draft where the type has drafts, and served,
and listed with a new `lastmod` in the sitemap, once the page is published.

To let someone edit a type's pages but not their SEO, turn `pagePermissions` on:

```ts
seoPlugin({ collections: ["posts"], pagePermissions: true });
```

Each content type the plugin extends then has its own `edit-seo-<type>` permission. A role that
may update a page and lacks it saves everything else on the page, while the page's SEO stays as it
was, and the SEO tab shows it read-only. Reading a page's SEO stays part of reading the page.

Which built-in roles hold what:

- **Super Admin** and **Admin** hold every permission the plugin declares.
- **Editor**, **Author** and **Viewer** hold none of the three above, since the built-in roles
  other than Admin never pick up a permission a plugin declares. Editors and Authors change a
  page's SEO with the page while `pagePermissions` is off, and none of them reaches site-wide SEO
  or the check. Give the people who should a role of your own holding the permissions above.

The sitemap, robots.txt and each page's head are public. Making a [share image](#share-images-of-the-right-size)
is a change to the media library, asked as `create-media` and `read-media`.

An admin menu entry or screen can ask one permission. The settings screen asks `manage-seo`, so
someone holding it without `read-seo-settings` sees the entry, and the screen is refused its
contents.

## Pages built in code

A page a route renders from its own code, such as `/pricing` in `app/pricing/page.tsx`, has
no entry to hold its SEO. Its SEO is set by address instead, on the **Pages and addresses**
screen, under SEO in the admin. The screen lists every public address the site knows of:
each entry's, each route with no variable part (`/pricing`), and each address a route with
one declares through `generateStaticParams` (`/integrations/wordpress`). Choose **Edit SEO**
on a page built in code to set its title, description, visibility and share image. The
screen and its saves ask `manage-seo`.

What is set there reaches the page once its route adds one line, calling `seoMetadata` with
its address:

```tsx
// src/app/pricing/page.tsx
import { seoMetadata } from "@nextlyhq/plugin-seo";

export const generateMetadata = () =>
  seoMetadata("/pricing", {
    metadata: { title: "Pricing", description: "Plans for every team." },
  });

export default function PricingPage() {
  return <h1>Pricing</h1>;
}
```

A route with a variable part calls it for the address it is serving:

```tsx
// src/app/integrations/[name]/page.tsx
import { seoMetadata } from "@nextlyhq/plugin-seo";

export const generateStaticParams = () => [
  { name: "wordpress" },
  { name: "webflow" },
];

export async function generateMetadata({
  params,
}: {
  params: Promise<{ name: string }>;
}) {
  const { name } = await params;
  return seoMetadata(`/integrations/${name}`);
}

export default function IntegrationPage() {
  return <h1>Integration</h1>;
}
```

The page is answered by the same order of who wins as every page with an entry:

- what a person set on the screen wins;
- the route's own title, description and social values come next. Anything else the route
  sets, such as keywords, is kept as it is;
- then the site's [title pattern](#title-patterns) with the page's name, taken from its
  address (`/thank-you` is "Thank you") or given as `name`, and the site's defaults.

Visibility and the canonical come only from the answer, never from the route: the canonical
is the page's own address, and a page is hidden only from the screen. A save on the screen
reaches the page from its next visit, a page built ahead of time included.

The screen marks **Not connected** each route that has not called `seoMetadata`. What is set
for its address is kept, and reaches the page once the line is in. A route records that it is
connected when it renders: while `next build` renders the site, or later for an address the
site knows of. A request for any other address records nothing.

<Callout type="info">
**The list of routes comes from the build.** The plugin reads the routes and the addresses
they declared from what `next build` wrote, so the full list is that of a production build.
Under `next dev`, it holds only the routes compiled so far. If `next.config` sets `distDir`,
pass the same directory as `nextBuildDir`.

</Callout>
