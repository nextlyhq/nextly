---
title: Schema & data lifecycle
description: Contribute collections, extend existing entities (including Builder-made ones), relate across the merged schema, and clean up safely on uninstall.
---

A plugin's schema contributions flow through the **same unified merge pipeline** as your
app's own code-first schema and the Visual Schema Builder's schema (D3). The host can read them
*without running your plugin*, so the admin and codegen can reason about them.

## Contribute new entities

```ts
import { defineCollection, text, select } from "nextly";
import { definePlugin } from "@nextlyhq/plugin-sdk";

const Redirects = defineCollection({
  slug: "redirects",
  fields: [
    text({ name: "fromPath", required: true }),
    text({ name: "toPath", required: true }),
    select({
      name: "type",
      options: [
        { label: "301 (Permanent)", value: "permanent" },
        { label: "302 (Temporary)", value: "temporary" },
      ],
      defaultValue: "permanent",
    }),
  ],
});

definePlugin({
  name: "@acme/nextly-plugin-redirects",
  version: "1.0.0",
  nextly: ">=0.0.2-alpha.63",
  // ...
  contributes: {
    collections: [Redirects], // also: singles, fieldGroups
  },
});
```

CRUD permissions are auto-seeded per contributed collection/single. The collection is
tagged with your plugin's [provenance](#provenance) and locked from Builder editing
(it's plugin-managed).

## Extend existing entities

`contributes.extend` adds fields to an entity you don't own, by slug (D12):

```ts
contributes: {
  extend: [
    {
      target: "posts",
      fields: [text({ name: "metaTitle" }), text({ name: "metaDescription" })],
    },
    // target can be an array to extend several at once
  ],
}
```

As of the Builder schema lane (P8), `extend` may target a **Builder-made collection**,
not just a code-first one — the extra fields materialize (a migration adds the columns)
and are present at runtime. The added fields are attributed to your plugin in provenance,
so they're cleaned up if your plugin is removed.

> Extending an entity that doesn't exist in the merged schema is a **fail-fast boot
> error** — see the [error reference](/docs/plugins/error-reference).

## Migrations & databases

A plugin doesn't write SQL or manage tables itself — it **declares** schema through
`contributes`, and the host materializes it through the normal Nextly migration workflow:

```bash
nextly migrate        # generate + apply migrations for the merged schema (incl. plugins)
```

When a consuming app adds your plugin (or you change your contributed schema) and runs
`nextly migrate`, the plugin's collections and `extend` fields are folded into the merged
schema and turned into migrations alongside the app's own. The same plugin works across
Nextly's supported databases (PostgreSQL, MySQL, SQLite) because it goes through the
managed pipeline rather than dialect-specific SQL — **but** SQLite doesn't enforce some
constraints that Postgres/MySQL do, so test against a real database too (see
[Testing](/docs/plugins/testing)).

> Schema changes are applied on `migrate`, not silently at boot — first boot only
> **creates** missing tables; it never **alters** an existing one. Ship schema changes as
> migrations so existing installs pick them up.

## Relate across the merged schema

A plugin relationship (`relationship(...)`) may target **any** slug in the merged schema
— core (`users`, `media`), another plugin's collection, an app collection, or a
Builder-made one (D15). Targets are validated at boot; an unknown `relationTo` fails
fast.

## Reference your own slugs via `ctx.self`

Never hardcode your own collection slugs in `init`/handlers — an integrator can rename
them with `plugin.rename({...})` (D54). Read the resolved slug from `ctx.self`:

```ts
const slug = ctx.self.collections.redirects; // resolved, post-rename
await ctx.services.collections.listEntries(slug, {}, { as: "system" });

declare const ctx: PluginContext;
import type { PluginContext } from "@nextlyhq/plugin-sdk";
```

## Provenance (D14)

Every schema entity carries a `source`: `"code"`, `"ui"` (Builder), `"built-in"`, or
`"plugin:<name>"`. This is what makes uninstall safe — Nextly knows which tables, fields,
and permissions belong to which plugin, and never touches the user's own (`code`/`ui`)
data.

## Uninstalling & data cleanup

When you remove a plugin from `defineConfig({ plugins })`, its contributed tables become
**orphans** — present in the database, but no longer claimed by any registered plugin.
Nextly does **not** auto-drop them (your data is never deleted behind your back). Use the
`prune` CLI to review and remove them:

```bash
nextly prune           # dry run — lists orphaned plugin:* tables/columns/permissions
nextly prune --force   # actually drops them (and their data + seeded permissions)
```

`prune` only ever targets `plugin:<name>` provenance. Code-first (`code`) and
Builder (`ui`) entities are **always retained** — they're yours, not the plugin's. This
is why declaring everything through `contributes` (rather than hand-writing tables via
`ctx.db`) matters: it's what lets uninstall be clean and reversible.

> **Tip for plugin authors:** anything you create through `contributes` /
> `ctx.services` is provenance-tagged and pruned automatically. Anything you create by
> reaching into `ctx.db` (raw DDL, side tables) is **not** tracked and will be left
> behind on uninstall — document it, or avoid it.

See also: [Data access](/docs/plugins/services) · [Testing](/docs/plugins/testing).

## Tables of your own

A collection gives you REST routes, admin screens, validation and access
control. Sometimes you want none of that — a join table, a cache, a log a user
never sees — and a collection is the wrong shape for it.

Declare a table instead:

```ts
import { definePlugin } from "@nextlyhq/plugin-sdk";
import { col, defineTable } from "@nextlyhq/plugin-sdk/schema";

const identities = defineTable(
  "identities",
  {
    id: col.id(),
    provider: col.shortText(),
    providerAccountId: col.shortText(),
    userId: col.ref("users"),
    lastSeenAt: col.timestamp({ nullable: true }),
    ...col.timestamps(),
  },
  {
    indexes: [
      { columns: ["provider", "providerAccountId"], unique: true },
      { columns: ["userId"] },
    ],
  }
);

definePlugin({
  name: "@acme/nextly-plugin-auth",
  version: "1.0.0",
  nextly: ">=0.1.0",
  contributes: {
    schema: { prefix: "auth", tables: [identities] },
  },
});
```

That table is created as `auth__identities`. The prefix is yours; declare it,
or let it default to your plugin's admin slug.

### The column kinds

`text`, `shortText`, `longText`, `varchar(n)`, `boolean`, `integer`, `double`,
`decimal(p, s)`, `timestamp`, `json<T>()`, plus two conveniences: `col.id()` (a
`varchar(36)` primary key for a UUIDv7) and `col.timestamps()` (`created_at`
and `updated_at`).

The list is deliberately short. Every kind here renders on PostgreSQL, MySQL
and SQLite, so a table you declare works on all three — what cannot be
expressed cannot drift between them.

## Reading and writing

The declaration creates and migrates the table under its SQL name
(`auth__identities` above). Plugin code queries it through `ctx.db`, the
Drizzle builder, with a Drizzle table object that names the same table and
columns. `col.id()` has no database default, so the code that inserts a row
supplies its `id`.

## Hooks, when a declaration is not enough

`contributes.schema.extend` runs after every plugin before you in dependency
order, so you can react to what they declared:

```ts
contributes: {
  schema: {
    extend: [
      ({ schema }) => {
        schema.extendTable("dc_posts", {
          indexes: [{ columns: ["authorId", "publishedAt"] }],
        });
      },
    ],
  },
}
```

The declarative `tables` form is sugar for a hook calling `addTable`. They
produce identical output.

## What you may change

| Target | Columns | Indexes |
| --- | --- | --- |
| Your own tables | yes | yes |
| A plugin you name in `dependsOn` / `optionalDependsOn` | yes, hidden | yes |
| Any other plugin's tables | no | no |
| Entity tables (`dc_*`, `single_*`, `comp_*`) | yes, hidden | yes |
| Extendable core tables (`users`, `media`, `nextly_jobs`, `audit_log`, `activity_log`) | yes, hidden | yes |
| Every other core table | no | no |

The app may add columns and indexes to any plugin's table, under the same
rules.

Which migrations carry what you add depends on the table. On your own tables
and on a dependency's, your plugin's own migration modules carry it. On an
entity table or an extendable core table — whether a plugin or the app added
it — the APP's migrations carry it: `nextly migrate:create` in the app writes
the statement, so it reaches a database with the app's next migration.

A column added to a table you do not own is **hidden**: it exists on the table,
so migrations and dev push keep it, and on an entity table it is stripped
from every REST response, Direct API read, version snapshot and webhook
payload, and a value sent for it through the entry API is dropped. A `where`
naming it is refused, including under a component field's path for a column
on a component's table; a group key naming it is refused, and a sort by it is
ignored. The column
must be nullable or have a default, since the table may already have rows.

A hidden column is storage for your plugin's own bookkeeping, not a field. To
give a collection a field that editors and API callers see, with validation and
access control, use `contributes.extend`.

## What is deliberately unsupported

Views, native enums, and partial indexes: an index with a `where` predicate is
refused on every dialect, because declarations are checked against all three
and MySQL has none. Checks, foreign keys, and expression indexes ARE
supported: declare them on `defineTable` and they travel through
dev push, plugin migrations and drift checks on every dialect — inline in the
table's `CREATE TABLE` on its first migration, and through the table rebuild
where a dialect cannot add one in place. An expression index key must compute a
value: `DESC`, `ASC`, `NULLS FIRST/LAST`, `COLLATE` and operator classes such as
`text_pattern_ops` are refused at `defineTable`, because no dialect reports them
back and the index would be planned again on every push. `col.ref()` alone records a reference
for documentation and validation; a constraint comes from the `foreignKeys`
option.

## Production

A plugin that declares tables ships **migration modules**
(`contributes.schema.migrations`) and a `schemaVersion`. Generate them with
`nextly migrate:create --plugin ./src/index.ts`, bumping `schemaVersion` each
time; `nextly migrate` applies them in dependency order under the migrate lock,
before any plugin initialises. The ledger records them under qualified names
(`plugin:<name>/<file>`), an app rollback never touches them, and a production
boot refuses a plugin whose declared version the database has not applied
(`PLUGIN_SCHEMA_BEHIND`).

Generation never drops a table or column an earlier module created. The
generator cannot tell a rename from a drop and an add, and either loses the
rows, so it refuses (`PLUGIN_MIGRATION_DROPS_CREATED_SCHEMA`) and names what
it would have dropped; write the rename, or the deliberate drop, by hand. With
no schema changes it writes nothing and exits with code 2, whatever
`schemaVersion` says.

Each module runs in one transaction. A module that needs a statement a
transaction refuses, such as PostgreSQL's `CREATE INDEX CONCURRENTLY`, sets
`transaction: false`, and its UP and DOWN then run statement by statement. If
one fails, the statements before it stay applied and are not undone, so keep
such a module to the statements that need it. The field is part of the
module's checksum only when it is `false`, so existing modules keep their
checksums. See
[Running a file outside a transaction](/docs/guides/production-migrations#running-a-file-outside-a-transaction).

### Writing a module by hand

A generated module carries its checksum as a literal, and any edit to it is
refused (`MIGRATION_CHECKSUM_MISMATCH`). A module you write or edit yourself
is sealed by `migrationChecksum` from `@nextlyhq/plugin-sdk/schema` instead,
computed over the module without its checksum when the module loads:

```ts
import {
  migrationChecksum,
  type PluginMigration,
} from "@nextlyhq/plugin-sdk/schema";

const content = {
  name: "20261007_120000_000_index_notes",
  schemaVersion: 3,
  transaction: false,
  dialects: {
    postgresql: {
      up: ["CREATE INDEX CONCURRENTLY IF NOT EXISTS notes_label_idx ON acme__notes (label)"],
      down: ["DROP INDEX CONCURRENTLY IF EXISTS notes_label_idx"],
    },
    mysql: { up: [], down: [] },
    sqlite: { up: [], down: [] },
  },
  // The tables before and after it, carried from the previous module: an
  // index built outside a transaction changes no declared table.
  snapshot: {
    postgresql: { tables: [] },
    mysql: { tables: [] },
    sqlite: { tables: [] },
  },
  before: {
    postgresql: { tables: [] },
    mysql: { tables: [] },
    sqlite: { tables: [] },
  },
} satisfies Omit<PluginMigration, "checksum">;

export default {
  ...content,
  checksum: migrationChecksum(content),
} satisfies PluginMigration;
```

You rarely write one from nothing. `nextly migrate:create` writes it in this
form:

- `nextly migrate:create --plugin ./src/index.ts --blank` writes a module with
  no statements for SQL you add, such as a backfill or a `VACUUM`. It carries
  the previous module's schema on both sides, so its SQL must not change the
  tables the plugin declares; its `schemaVersion` is the plugin's, which may
  equal the previous module's. Add `--no-transaction` for a module with
  `transaction: false`.
- `nextly migrate:create --plugin ./src/index.ts --no-transaction` generates the
  next module from the plugin's schema, as usual, with `transaction: false`, so
  you can turn its `CREATE INDEX` into `CREATE INDEX CONCURRENTLY`. A statement
  that builds the same index leaves the module's snapshot correct.

Either way the module is written to `src/migrations/` and added to its barrel.
A hand-sealed module gives up one check: that its SQL is the SQL that was
generated. The ledger still refuses a module that changed after it was
applied, so finish editing it before it ships.

These rules hold for every module, and a plugin that breaks one is refused
when the configuration loads, before anything runs:

- Its `name` cannot contain `/`. The ledger records it as
  `plugin:<plugin>/<name>`, and a slash in the name would file it under
  another plugin.
- Its `schemaVersion` is a positive integer, as the plugin's own is, whether
  or not the plugin declares one.
- Modules run in name order — compared character by character, ignoring
  case, the same on every machine whatever its locale, so `10_more` runs
  before `1_init`: zero-pad a numbered name. When the plugin declares a
  `schemaVersion`, each module's is no lower than the one before it. The
  version the database ends at is the last module's, so it is the one that
  must equal the plugin's `schemaVersion`.

And when it runs, a module may drop or rename only what the owner registry
says is the plugin's: its own tables, and the indexes and constraints on
them; the columns, indexes, foreign keys and checks it contributed to other
owners' tables; and tables the module itself creates. A table no record
claims, such as an app table from before the registry, is refused
(`DROP_OF_FOREIGN_TABLE`), and so is a drop of another owner's index or
constraint — including an index named on its own (`DROP INDEX name`), whose
table is read from the database.

A database development push already brought to a plugin's latest shape is
adopted: `nextly migrate` records the modules it stands past as applied
without running them, since the tables already say they ran. That proof holds
only for what a schema shows. A module that only changes data — a seed or a
backfill, or one creating a trigger or function — runs where it stands
instead, against the tables as they are, and so does any module whose schema
does not change, such as one written with `--blank`, whatever its SQL. Such a
module therefore has to hold against every later shape of the plugin's tables;
one that fails there is refused with the recovery. A module that both changes
the schema and does such work can be neither, and is refused with the
recovery; keep data statements in modules of their own.

The entry `--plugin` points at may export the plugin as its default export or
as a named one (`export const myPlugin = definePlugin(...)`), beside the tables
it declares; a file exporting two plugins is refused, naming both.

A database that dev push has already given the plugin's tables can be migrated
as it is. Dev push creates the tables as the plugin defines them now, which is
the result of its latest module, so `nextly migrate` records every module up to
the one whose result the database matches as applied, without running them,
and runs any after it. A database matching no point in the plugin's history is
refused, with the recovery for a plugin's tables.
