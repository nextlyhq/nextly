The Form Builder plugin adds a complete form management system to Nextly. Build forms visually in the admin panel or define them in code, collect submissions, send email notifications, and protect against spam -- all without writing custom endpoints.

## Installation

```bash
npm install @nextlyhq/plugin-form-builder
```

The plugin declares these peer dependencies:

| Peer                    | Range                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `nextly`                | the matching lockstep version, pinned exactly                                          |
| `@nextlyhq/admin`       | the matching lockstep version, pinned exactly                                          |
| `@nextlyhq/plugin-sdk`  | the matching lockstep version, pinned exactly                                          |
| `@nextlyhq/ui`          | a caret range on the matching lockstep version                                         |
| `@tanstack/react-query` | >= 5                                                                                   |
| `lucide-react`          | >= 0.400.0                                                                             |
| `react`                 | the supported range in [Requirements](/docs/getting-started/installation#requirements) |
| `next`                  | the supported range in [Requirements](/docs/getting-started/installation#requirements) |

Nextly peers are pinned to the exact version the plugin was built against, and `@nextlyhq/ui`

version rather than reaching for a range of your own. `@tanstack/react-query` and
`lucide-react` are the two most likely to be missing from a project that has not needed
them yet, and their absence shows up as a broken admin screen rather than an install
error.

## Basic Setup

```typescript
// nextly.config.ts
import { defineConfig } from "nextly";
import { formBuilder } from "@nextlyhq/plugin-form-builder";

const fb = formBuilder();

export default defineConfig({
  plugins: [fb.plugin],
  collections: [Posts, Users, Media],
});
```

This creates two collections automatically:

| Collection  | Default Slug       | Purpose                                                   |
| ----------- | ------------------ | --------------------------------------------------------- |
| Forms       | `forms`            | Stores form definitions (fields, settings, notifications) |
| Submissions | `form-submissions` | Stores submitted data with status tracking                |

Both collections appear in the admin sidebar under the **Forms** group.

## Configuration Options

Pass an options object to `formBuilder()` to customize behavior.

```typescript
// nextly.config.ts
const fb = formBuilder({
  // Customize collection slugs and labels
  formOverrides: {
    slug: "contact-forms",
    labels: { singular: "Contact Form", plural: "Contact Forms" },
  },
  formSubmissionOverrides: {
    slug: "responses",
    labels: { singular: "Response", plural: "Responses" },
  },

  // Enable/disable specific field types
  fields: {
    file: false, // Disable file uploads
    hidden: false, // Disable hidden fields
  },

  // Email notifications
  notifications: {
    defaultFrom: "noreply@example.com",
    defaultToEmail: "submissions@example.com",
    enabled: true,
  },

  // Spam protection
  spamProtection: {
    honeypot: true,
    rateLimit: {
      maxSubmissions: 10,
      windowMs: 60_000,
    },
  },

  // File upload limits
  uploads: {
    maxFileSize: 10_485_760, // 10 MB
    allowedMimeTypes: ["image/*", "application/pdf", "text/*"],
    uploadCollection: "media",
  },

  // Feature flags
  features: {
    builder: true,
    conditionalLogic: true,
    fileUploads: true,
  },

  // Collections that can serve as redirect targets after submission
  redirectRelationships: ["pages"],
});
```

### Collection Overrides

You can add custom fields to the Forms or Submissions collections, or restrict access control.

**Array style** -- appends fields to the defaults:

```typescript
formOverrides: {
  fields: [
    text({ name: 'internalNotes', label: 'Internal Notes' }),
  ],
  access: {
    read: () => true,
    create: ({ permissions }) => permissions.includes('create-forms'),
  },
}
```

By default a visitor can read a form and create a submission. Everything else needs the
matching permission on the Roles screen: `read-form-submissions` to read submissions,
`update-forms` to edit a form, `delete-form-submissions` to delete one. An override narrows
from there; check the permission in it rather than a role's name.

**Function style** -- full control over the field list:

```typescript
formSubmissionOverrides: {
  fields: ({ defaultFields }) => {
    const formIndex = defaultFields.findIndex(f => f.name === 'form');
    return [
      ...defaultFields.slice(0, formIndex + 1),
      { name: 'source', type: 'text' },
      ...defaultFields.slice(formIndex + 1),
    ];
  },
}
```

## Field Types

All 14 field types are enabled by default. Set any to `false` in the `fields` option to remove it from the builder.

| Type       | Description                          | Key Options                         |
| ---------- | ------------------------------------ | ----------------------------------- |
| `text`     | Single-line text input               | `minLength`, `maxLength`, `pattern` |
| `email`    | Email address with format validation | `pattern`                           |
| `number`   | Numeric input                        | `min`, `max`, `step`                |
| `phone`    | Phone number input                   | `pattern`                           |
| `url`      | URL with format validation           | `pattern`                           |
| `textarea` | Multi-line text input                | `rows`, `minLength`, `maxLength`    |
| `select`   | Dropdown menu                        | `options`, `allowMultiple`          |
| `checkbox` | Single boolean toggle                | `defaultValue`                      |
| `radio`    | Radio button group                   | `options`                           |
| `file`     | File upload                          | `accept`, `multiple`, `maxFileSize` |
| `date`     | Date picker                          | `min`, `max`                        |
| `time`     | Time picker                          | `defaultValue` (HH:mm format)       |
| `hidden`   | Hidden value (not shown to users)    | `defaultValue`                      |
| `consent`  | Required box agreeing to a text      | `agreementText`                     |

Every field supports these common properties: `name`, `label`, `placeholder`, `helpText`, `defaultValue`, `required`, `validation`, `conditionalLogic`, and `admin.width` (25% to 100%).

## Creating Forms

### Visual form builder (admin UI)

Navigate to **Forms** in the admin sidebar and click **Create New**. The form builder provides:

- **Field Library** -- click or drag field types to add them to the form
- **Form Canvas** -- reorder fields with drag-and-drop, click to edit
- **Field Editor** -- configure each field's label, validation, placeholder, help text, and conditional logic
- **Settings Tab** -- submit button text, confirmation type (message or redirect), multiple submission settings
- **Notifications Tab** -- configure email integrations per form
- **Preview** -- see how the form will look to end users

Forms have three statuses:

- **Draft** -- not accepting submissions (use for building)
- **Published** -- live and accepting submissions
- **Closed** -- shows a configurable closed message

### Code-First Definitions

Use the field helper functions to define forms programmatically. These helpers set the `type` property automatically.

```typescript
import {
  text,
  email,
  textarea,
  select,
  checkbox,
  option,
} from "@nextlyhq/plugin-form-builder";

const contactFields = [
  text({ name: "firstName", label: "First Name", required: true }),
  text({ name: "lastName", label: "Last Name", required: true }),
  email({ name: "email", label: "Email Address", required: true }),
  select({
    name: "subject",
    label: "Subject",
    required: true,
    options: [
      option("General Inquiry"),
      option("Support Request"),
      option("Feedback"),
    ],
  }),
  textarea({
    name: "message",
    label: "Message",
    required: true,
    rows: 5,
    validation: { minLength: 10, maxLength: 2000 },
  }),
  checkbox({ name: "subscribe", label: "Subscribe to our newsletter" }),
];
```

The `option()` helper converts labels to slug values automatically (`'General Inquiry'` becomes `'general_inquiry'`). Pass a second argument for an explicit value: `option('United States', 'us')`.

Additional field helpers: `number()`, `phone()`, `url()`, `radio()`, `file()`, `date()`, `time()`, `hidden()`, `consent()`.

### Consent fields

A consent field is a box the visitor ticks to agree to a text, such as your privacy policy. It is always required. The answer stores the choice with the text the form showed, so changing the text later leaves what earlier visitors agreed to as it was:

```typescript
import { consent } from "@nextlyhq/plugin-form-builder";

consent({
  name: "privacy",
  label: "Privacy",
  agreementText: "I agree to the privacy policy",
});
// A submission stores: { privacy: { agreed: true, text: "I agree to the privacy policy" } }
```

The text comes from the form, never from what the visitor sends. A site that renders the form can send the text it showed with the answer, `{ "agreed": true, "text": "I agree to the privacy policy" }`: if the author changed the text while the form was open, the submission is refused, asking the visitor to review it and agree again, rather than recorded as agreement to terms they never saw. A plain checkbox value (`on`, `true`) is taken as agreement to the text the form shows when it arrives. A submitted consent cannot be edited: an update that would change or drop it, from the admin or the API, is refused with a validation error, and an edit of other answers keeps it as it was.

### Utility Functions

Create a complete form config with defaults applied in one call:

```typescript
import { createFormConfig } from "@nextlyhq/plugin-form-builder";

const contactForm = createFormConfig("contact", contactFields, {
  settings: {
    submitButtonText: "Send Message",
    confirmationType: "message",
    successMessage: "Thanks! We will get back to you within 24 hours.",
  },
});
```

Validate a form config before saving:

```typescript
import {
  validateFormConfig,
  assertValidFormConfig,
} from "@nextlyhq/plugin-form-builder";

const result = validateFormConfig(contactForm);
if (!result.valid) {
  console.error(result.errors);
}

// Or throw on invalid config
assertValidFormConfig(contactForm);
```

## Form Submissions

The handlers below take a `{ pluginContext, pluginConfig }` context. `pluginContext` is the `ctx` your code already receives from the plugin system -- for example a [plugin route handler](/docs/plugins/routes)'s `(req, ctx) => ...`, or your own plugin's `init(ctx)`. `pluginConfig` is the object `formBuilder()` returned: keep the result and use `fb.config`. Note that `getFormBuilderConfig(ctx)` is **not** an alternative from another plugin's context — the resolved config is written onto the form-builder's own context during its `init`, and `initializePlugins` gives every plugin a separate one, so that call returns `undefined` anywhere else.

### Handling Submissions

Use the `submitForm` handler to process submissions server-side. It runs the full pipeline: fetch form, validate data, check spam, store submission, and determine redirect.

```typescript
import { submitForm } from "@nextlyhq/plugin-form-builder";
import type { PluginContext } from "@nextlyhq/plugin-sdk";
import type { ResolvedFormBuilderConfig } from "@nextlyhq/plugin-form-builder";

declare const request: Request;
declare const pluginContext: PluginContext;
declare const pluginConfig: ResolvedFormBuilderConfig;

const result = await submitForm(
  {
    formSlug: "contact",
    data: { firstName: "Jane", email: "jane@example.com", message: "Hello!" },
    // The language the visitor submitted in. A picked redirect page is read in
    // it, so a page whose slug is `thanks` in English and `merci` in French
    // sends a French visitor to `/merci`. Pass whatever you resolved for the
    // page the form was on; the built-in route reads it from `?locale=`.
    locale: "fr",
    metadata: {
      // No ipAddress here on purpose: see "Where the IP has to come from"
      // below. Reading `x-forwarded-for` straight off the request is the one
      // thing not to do.
      userAgent: request.headers.get("user-agent") || undefined,
    },
  },
  { pluginContext, pluginConfig }
);

if (result.success) {
  if (result.redirect) {
    // Redirect the user
  }
  // result.submission contains the stored document
} else {
  // result.error and result.validationErrors describe what went wrong
}
```

### Where the IP has to come from

`submitForm` keys two protections on `metadata.ipAddress`: the per-IP rate limit,
and one response per network (below). It also stores the value on the submission.

That makes the header a control input, not a log field. `x-forwarded-for` is
client-supplied on a direct request and on any proxy that forwards it verbatim, so
a bot that varies it on every request gets a fresh rate-limit bucket each time and
walks past a limit that looks configured. Nextly closed exactly this in its own
auth and rate-limit paths, which is why `getTrustedClientIp` exists:

```ts
// nextly.config.ts, or anywhere the application itself runs
import { getTrustedClientIp, parseTrustedProxyIpsEnv } from "nextly";

declare const request: Request;
declare const trustProxy: boolean;

const ipAddress =
  getTrustedClientIp(request, {
    trustProxy,
    trustedProxyIps: parseTrustedProxyIpsEnv(process.env.TRUSTED_PROXY_IPS),
  }) ?? undefined;
```

It walks the forwarded chain from the right, skipping hops in `TRUSTED_PROXY_IPS`,
and returns the first one you did not vouch for. It returns `null` when it cannot
identify a client, and passing `undefined` on is the correct thing to do with that:
the limiter skips a submission it cannot attribute rather than filing every unknown
caller in one bucket.

Two consequences worth stating plainly. `security.trustProxy` defaults to `false`,
so until you set it and list your proxies the resolver returns `null` and the rate
limit does not run. And `getTrustedClientIp` ships from `nextly`, not from
`@nextlyhq/plugin-sdk`, so a distributed plugin cannot reach it through the surface
it is supposed to depend on. An application that hosts its own route, as below, can.

### One response per person

A form's Settings can limit each person to one response. The server compares a keyed one-way digest of what tells people apart, never the value itself, and a unique index refuses a second submission with the same digest when it is stored, so two sent at once cannot both get in.

| Setting (`settings.oneResponse`) | Compares | Notes |
| --- | --- | --- |
| `off` | nothing | The default: anyone may respond again. |
| `email` | the answer to the chosen Email field (`settings.oneResponseField`), ignoring case | The field must be required and not hidden by a condition, so every response carries an address. Saving a form that breaks this is refused, and the builder will not delete the field, make it optional or give it a condition while it is chosen. |
| `ip` | the network address | People sharing an office or home network count as one. Needs the trusted IP above. |
| `browser` | a token the visitor's browser keeps | Counted from when it is chosen. Someone who clears their browser's data, or uses another browser, can respond again. |

A second response is refused: `submitForm` answers `outcome: "duplicate"`, and the built-in route answers `409` with the message "You have already submitted this form." A submission marked spam gives its place back.

**One per browser needs your form's script.** For a form that compares browsers, the public read of the form (`GET /api/forms/:slug`) says where the token goes:

```json
{
  "oneResponse": { "by": "browser", "field": "nextly-browser-token" }
}
```

Keep one random token per form in the visitor's browser, and send it inside `data` under that field:

```ts
// One token per form, so a browser's responses to two forms cannot be linked.
function browserToken(formSlug: string): string | undefined {
  const name = `nextly-browser-token:${formSlug}`;
  try {
    const kept = window.localStorage.getItem(name);
    if (kept) return kept;
    const made = crypto.randomUUID();
    window.localStorage.setItem(name, made);
    return made;
  } catch {
    // Storage blocked: send no token.
    return undefined;
  }
}

async function send(formSlug: string, answers: Record<string, unknown>) {
  const token = browserToken(formSlug);
  return fetch(`/api/forms/${formSlug}/submit`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({
      data: token ? { ...answers, "nextly-browser-token": token } : answers,
    }),
  });
}
```

The token must be 16 to 128 letters, digits, `-` or `_` (`crypto.randomUUID()` is one). It is never stored with the submission. A submission that comes without a token, or with a malformed one, is accepted without the check, as a browser that cleared its data would be, and the server logs a warning so a form whose script does not send it is noticed.

**Changing the setting counts earlier responses.** Choosing one per network, or changing to it from another setting, counts the submissions already stored by their stored address. Earlier responses count for one per email address too, once Settings offers it. Of several earlier submissions with the same value, the earliest keeps it. One per browser counts from when it is chosen, since no earlier token was kept.

A form with up to 200 submissions is brought up to date inside the save itself. A larger one is finished by the plugin's background sweep (`form-builder:one-response-keys`), which the job runner carries on. Until then each new submission is compared with the earlier ones directly, so nobody gets a second response in the meantime. Set the size with the plugin's `oneResponse.keysInSave` option:

```typescript
formBuilder({
  oneResponse: { keysInSave: 50 },
});
```

When the sweep finishes it records that on the form, which moves the form's revision on. The admin's form editor saves on through that: if nothing it sends has changed, it saves again on the new revision. Your own code that saves forms with `_rev` should do the same: read the form again and retry.

**When a response stops counting.** If the submission holding a value is deleted, marked as spam, or edited to another address, the earliest other submission with the same value takes its place. A person who sent two responses before the form compared them still can't send a third.

If a form's setting changes while a submission is on its way, the submission is refused with "This form's settings changed while your response was being sent. Please send it again." and is judged by the new setting when it is sent again.

### Privacy: not keeping IP addresses

A form's **Settings › Privacy › Store IP address and browser** (`settings.storeIpAndBrowser`, on by default) decides whether a new submission keeps the address it came from and the visitor's browser. Off, it keeps neither. One per network still works on such a form: the address's keyed digest is made before the address is dropped, and only the digest is stored. Earlier submissions keep what they stored. A form that keeps no addresses cannot count its earlier responses by network after a change of setting, since it has none to count.

### Privacy: deleting old submissions

**Settings › Privacy › Delete submissions after** (`settings.keepDays`: Never, 30 days, 90 days or 1 year; none keeps them) sets how long a form keeps its submissions. A pass the plugin schedules each night (the job `form-builder:retention`, on the `@daily` schedule `form-builder-retention-nightly`) deletes every submission older than its form keeps them for, and spam older than 30 days whatever the setting. Age is when the submission was stored (`createdAt`).

Each one is deleted the way any deletion is, so what it sent goes with it, and so do the files it holds (see [File uploads](#file-uploads)). The pass also deletes the uploads no submission claimed within a day, and finishes any file an earlier deletion could not remove. A pass that runs out of time queues its own continuation, and the next jobs run carries on. Like every schedule, it runs only while something calls the jobs route (`/admin/api/jobs/run` in a scaffolded app); a night missed is caught up by the next one, which deletes everything past keeping by then.

### File uploads

A `file` field's answer is a media id, or a list of them for a field with `multiple`. The visitor's browser uploads each file first, through a route the plugin contributes, and puts the id it answers with in the submission:

```
POST /admin/api/forms/:slug/upload
Content-Type: multipart/form-data
```

| Part    | What it is                                         |
| ------- | -------------------------------------------------- |
| `field` | The name of one of the form's `file` fields.       |
| `file`  | The file. One per request; upload several in turn. |

It answers `201` with `{ message, mediaId, field, filename, mimeType, size }`. The file is refused unless:

- the form exists and takes submissions now: a form that is not published, or one that has closed, answers as submitting to it would (`404`, or `409` with its closed message);
- `field` names one of the form's file fields (`400`, error path `field`), and file uploads are enabled (`features.fileUploads` and `fields.file`);
- the file is one the field takes (`400`, error path `file`): a type its `accept` lists (`.pdf`, `image/*`, `application/pdf`; the plugin's `uploads.allowedMimeTypes` when it lists none), no larger than its `maxFileSize`, which can never exceed the plugin's `uploads.maxFileSize` (10 MB by default) and is that when the field sets none. A body larger than the limit is refused without being read whole;
- the visitor is within the rate limit: five uploads per submission `spamProtection.rateLimit` allows, per visitor and form, in the same window (`429`). As with submissions, a visitor whose address cannot be trusted is not limited.

The file is stored in the media library as the plugin, and is judged there as every upload is: its contents against its type, blocked types, and its name. Its type is checked against the field again on what the library stored.

The plugin records each upload, and a submission's file answer may only name uploads made through this route for the same form and field that no other submission has claimed. Anything else, such as another form's upload, an upload already part of another submission, or the id of a file the site uses, refuses the submission with a validation error on that field ("This file was not uploaded for this field. Please upload it again."). This holds for a visitor submitting and for staff writing through the API. An edit keeps the files a submission already holds: an update may send a field's stored ids back unchanged. A submission flagged as spam is stored without the refusal, as it is stored without validation.

A write no request produced (the Direct API from your own server code, an import, a job) is trusted, as it was before uploads were recorded: nothing it names is refused, and an upload it names for the same form and field that no submission has claimed is claimed for it, so the file stays with that submission.

Deleting a submission deletes the files it holds, whichever way it is deleted: one at a time, in bulk, by the nightly pass, or with its form. The file is deleted once the deletion has committed, and only if nothing else uses it (a document's field, an avatar, a logo); a file in use is kept, and checked again each night. An upload no submission claims within a day is deleted by the nightly pass. A file the submission names without holding it (one a trusted write named that was not uploaded through the route, or was already another submission's, and any file a submission stored before uploads were recorded names) is not deleted with it.

The plugin ships no front-end form of its own, so your site's form does the upload. For example:

```typescript
async function uploadThenSubmit(form: HTMLFormElement, slug: string) {
  const answers: Record<string, unknown> = {};
  for (const [name, value] of new FormData(form)) {
    if (!(value instanceof File)) {
      answers[name] = value;
      continue;
    }
    if (value.size === 0) continue;
    const body = new FormData();
    body.append("field", name);
    body.append("file", value);
    const res = await fetch(`/admin/api/forms/${slug}/upload`, {
      method: "POST",
      body,
    });
    if (!res.ok) throw new Error((await res.json()).error.message);
    const { mediaId } = (await res.json()) as { mediaId: string };
    // A field with `multiple` answers with a list of ids.
    answers[name] = mediaId;
  }
  await fetch(`/admin/api/forms/${slug}/submit`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ data: answers }),
  });
}
```

### Validation

The plugin generates [Zod](https://zod.dev) schemas from form field definitions at runtime. Every submission is validated against the schema before storage, and free-text fields are sanitized by stripping HTML tags to prevent injection.

That happens on a `beforeChange` hook on the submissions collection, the last collection-level mutating phase before the insert, so it applies to every way a submission can be written: your own route calling `submitForm`, the built-in `POST /admin/api/forms/:slug/submit`, `nextly.forms.submit()`, an admin editing a stored submission, and a record created from the admin. A submission is also projected onto the fields the form declares, so a key the form does not define is dropped rather than stored. Field-level `beforeChange` hooks run after this one and are handed the whole record, so one you register on this collection yourself is trusted the way core trusts a field hook on any other collection.

Values are sanitized before they are validated, so every rule judges the value that will actually be stored rather than the one that arrived.

A submission flagged as spam is stored without being validated, deliberately, so a false positive stays reviewable rather than being thrown away. That exception ends when the row leaves spam: marking one "Not spam" checks the payload it is carrying against the form, so a row that never satisfied the form has to be corrected in the same edit before it can become an ordinary counted submission.

Spam protection runs on the same hook, and is decided BEFORE the payload is validated. A bot that trips the honeypot while also omitting a required field is stored flagged rather than answered with a validation error, because an error tells it which of the two it got wrong.

The honeypot and the rate limit are facts about an HTTP REQUEST rather than about a row, so they stand down when no request produced the write: a trusted server importing a thousand submissions does not rate-limit its own import, and a honeypot field means nothing without a browser to have skipped it. What separates the two is whether a request reached the hook, not which function was called.

You do not need a route of your own to get any of it. `POST /admin/api/forms/:slug/submit` is contributed by this plugin and calls `submitForm`, so a browser posting to it meets the honeypot and the rate limit exactly as one posting to a route you host yourself would. Host your own when you want a different response shape or extra work around the submission, not to obtain spam protection.

The plugin's routes sit directly under wherever your app mounts `createDynamicHandlers`, which a scaffolded project does at `src/app/admin/api/[[...params]]/route.ts`: hence `/admin/api`. A bare `/api/forms/...` is a 404 there (see [Routes](/docs/plugins/routes)).

On a localized site, post to `/admin/api/forms/:slug/submit?locale=fr` from a French page. The locale decides which translation the redirect target is read in, so the visitor lands on that page's French URL; a submission that names none is answered in the default language. A code the site does not have reads as the default rather than refusing the submission — the visitor filled the form in, and a wrong query string is not a reason to lose it. The target is read as the visitor, so a translation that is still a draft is not where they are sent: the published default answers until the translation is published.

You can validate data without creating a submission:

```typescript
import { validateSubmission } from "@nextlyhq/plugin-form-builder";
import type { PluginContext } from "@nextlyhq/plugin-sdk";
import type { ResolvedFormBuilderConfig } from "@nextlyhq/plugin-form-builder";

declare const pluginContext: PluginContext;
declare const pluginConfig: ResolvedFormBuilderConfig;

const { valid, errors } = await validateSubmission(
  "contact",
  { firstName: "Jane", email: "not-an-email" },
  { pluginContext, pluginConfig }
);
```

### Submission Status

Each submission tracks its review state:

| Status     | Description                          |
| ---------- | ------------------------------------ |
| `new`      | Unread submission                    |
| `read`     | Reviewed by an admin                 |
| `archived` | Archived (hidden from default views) |

Admins can also add internal notes to any submission -- these are not visible to the original submitter.

### Deleting submissions

Deleting a submission forgets the notifications it sent, in the same transaction: one not yet sent (waiting, retrying, or failed) is cancelled and its message cleared, so nothing goes out from data that is gone, and the delivery records of one that went out are erased. This holds for deleting one submission, deleting several at once, and deleting a form, which deletes its submissions with it.

It also deletes the files the submission holds, once the deletion has committed (see [File uploads](#file-uploads)).

The plugin keeps what each submission sent in an internal `form-submission-sends` collection, which no caller can read or write. Existing installations receive it through their own migrations: run `nextly migrate:create` and then `nextly migrate` (or `nextly db:sync` in development). A notification queued before the upgrade was not recorded, so deleting its submission does not forget it. The uploads made through the upload route are kept the same way, in an internal `form-uploads` collection, which existing installations receive through the same migration.

### Statistics

```typescript
import { getFormSubmissionStats } from "@nextlyhq/plugin-form-builder";
import type { PluginContext } from "@nextlyhq/plugin-sdk";
import type { ResolvedFormBuilderConfig } from "@nextlyhq/plugin-form-builder";

declare const pluginContext: PluginContext;
declare const pluginConfig: ResolvedFormBuilderConfig;

const stats = await getFormSubmissionStats("contact", {
  pluginContext,
  pluginConfig,
});
// { total: 42, new: 5, read: 30, archived: 7 }
```

## Email Notifications

Notifications are configured per form in the admin UI under the **Notifications** tab. Each notification integration specifies:

| Setting         | Description                                                                 |
| --------------- | --------------------------------------------------------------------------- |
| `templateSlug`  | Email template to use (from your [email configuration](/docs/guides/email)) |
| `recipientType` | `"static"` (fixed email) or `"field"` (value from a form field)             |
| `to`            | Email address, or `{{fieldName}}` reference when using field recipient      |
| `providerId`    | Email provider to use (optional, falls back to system default)              |
| `cc` / `bcc`    | Additional recipients                                                       |

Template variables available in your email templates: all submitted field values, plus `formName` and `submissionId`.

### Delivery and retries

Each notification is queued once its submission is saved, then sent at once. A failure that a retry can help (the provider is down, or times out) is not dropped: it is tried again, with a growing wait between attempts, until it is sent or fails for good. Retries run when your site calls the jobs trigger (`POST /admin/api/jobs/run`, see [Jobs](/docs/jobs)), so schedule that call on any site that sends form notifications. A refusal no retry can change, such as an invalid address, fails at once.

A notification that fails for good is logged twice, and the two lines share the queued email's id (`queuedId`): the Form Builder's line names the form and the notification, and the server's own `queued-email-failed` line gives the reason. Neither names a recipient.

### beforeEmail Hook

Modify or filter outgoing emails before they are sent:

```typescript
const fb = formBuilder({
  beforeEmail: async ({ emails, form, submission }) => {
    return emails.map(email => ({
      ...email,
      bcc: ["archive@example.com"],
    }));
  },
});
```

## Spam Protection

Three layers of protection: a honeypot and a rate limit, both on by default, and a bot check (Google reCAPTCHA v3 or Cloudflare Turnstile) once you configure its keys.

### Honeypot Fields

Hidden form fields that bots fill in automatically. When a honeypot field contains a value, the submission is stored flagged as spam and the bot receives an ordinary success response, so the detection is not revealed.

Standard honeypot field names checked: `__honeypot`, `_honeypot`, `honeypot`, `__hp`, `_hp`, `website`, `url_field`, `fax_number`.

### Rate Limiting

Limits submissions per IP address and form within a time window. Defaults to 10 submissions per 60 seconds per IP.

```typescript
spamProtection: {
  rateLimit: {
    maxSubmissions: 5,
    windowMs: 120_000, // 2 minutes
  },
}
```

The rate limit uses the deployment's shared rate-limit store, `rateLimit.store` in `defineConfig`, which falls back to memory. With several instances and no shared store, each instance counts on its own.

### Bot checks: reCAPTCHA and Turnstile

A bot check runs in the visitor's browser and gives the form a token, which the server verifies with the provider before the submission is accepted:

- **Google reCAPTCHA v3** scores each visitor in the background, with no puzzle to solve. A score below `scoreThreshold` (default `0.5`) fails.
- **Cloudflare Turnstile** checks each visitor in the background and rarely shows a puzzle.

Set each provider's keys in the plugin's options. `enabled` makes a provider the site default, which forms use unless their Settings choose another check or Off (reCAPTCHA wins when both are enabled):

```typescript
spamProtection: {
  recaptcha: {
    enabled: true,
    siteKey: 'your-recaptcha-site-key',
    secretKey: 'your-recaptcha-secret-key',
    scoreThreshold: 0.5,
  },
  turnstile: {
    enabled: false,
    siteKey: 'your-turnstile-site-key',
    secretKey: 'your-turnstile-secret-key',
  },
}
```

Setting a provider's `secretKey` also declares its verification host in the plugin's outbound allowlist (`www.google.com` or `challenges.cloudflare.com`). A site using neither gives the plugin no network access.

**Rendering the widget.** For a form whose check is on, the public read of the form (`GET /api/forms/:slug`) includes what the widget needs:

```json
{
  "botCheck": {
    "provider": "turnstile",
    "siteKey": "…",
    "field": "cf-turnstile-response"
  }
}
```

Render the provider's widget with that site key, and send its token inside `data` under `field`: `g-recaptcha-response` for reCAPTCHA or `cf-turnstile-response` for Turnstile, the names each provider's widget writes by default. It is never stored with the submission.

**What happens to a submission:**

- **Token passes:** accepted as usual.
- **Token fails or is missing:** stored flagged as spam (reason `recaptcha` or `turnstile`), as a honeypot hit is, so a false positive stays reviewable and the bot still sees a success.
- **Provider unreachable or answers something unexpected:** accepted unchecked and logged, so an outage does not send every real submission to spam.
- **Check on but the provider has no `secretKey`:** accepted unchecked, as before checks were verified. The server logs a warning at start naming the option to set, Settings says so on the form, and a check without its keys cannot be newly chosen in Settings.

The check is verified where every submission is stored, so it applies to the built-in route, `submitForm`, `nextly.forms.submit()` with a request, and the generic collection create. A server-side call with no request (an import) is not checked.

**Forms saved before this change** keep their protection. A form whose reCAPTCHA setting was left to the plugin follows the site default, one with reCAPTCHA on uses reCAPTCHA, and one with it off has no check. A form that stored its own reCAPTCHA site key keeps using it until the plugin's options give one, and its Settings ask to move it there.

## Conditional Logic

Fields can be shown or hidden based on the values of other fields. Configure conditional logic on any field through the admin UI or in code.

```typescript
import { text, select, option } from "@nextlyhq/plugin-form-builder";

const fields = [
  select({
    name: "contactMethod",
    label: "Preferred Contact Method",
    options: [option("Email"), option("Phone")],
  }),
  text({
    name: "phoneNumber",
    label: "Phone Number",
    conditionalLogic: {
      enabled: true,
      action: "show",
      operator: "AND",
      conditions: [
        { field: "contactMethod", comparison: "equals", value: "phone" },
      ],
    },
  }),
];
```

Supported comparison operators: `equals`, `notEquals`, `contains`, `isEmpty`, `isNotEmpty`, `greaterThan`, `lessThan`.

Multiple conditions can be combined with `AND` (all must match) or `OR` (any must match). The `action` property determines whether matching conditions **show** or **hide** the field.

## Webhooks

Form submissions are delivered through Nextly's own [webhooks](/docs/webhooks): subscribe an endpoint to the `form.submission.created` event. Its payload says which form, when, and the submission's status, and its `resource.id` names the submission (`resource.slug` is the submissions collection, `form-submissions` unless you renamed it). It never carries the answers, the IP address or the user agent, so a receiver that needs them reads the submission by that id:

- A receiver in another system calls the [REST API](/docs/api-reference/rest-api): `GET /admin/api/collections/form-submissions/entries/{id}`, authenticated with an [API key](/docs/api-reference/rest-api#api-key-server-to-server) that may read submissions (`read-form-submissions`).
- A receiver inside the same Next.js app can use the [Direct API](/docs/api-reference/direct-api) instead.

Verify each delivery's signature as the Webhooks page describes, before reading anything.

A form has no webhook settings of its own, and the submissions collection's default `entry.*` events are switched off, so an endpoint subscribed to `entry.created` or `*` does not receive the answers either.

## Example: Contact Form

A complete contact form setup from config to submission handling.

**1. Configure the plugin:**

```typescript
// nextly.config.ts
import { defineConfig } from "nextly";
import { formBuilder } from "@nextlyhq/plugin-form-builder";

const fb = formBuilder({
  notifications: {
    defaultFrom: "noreply@mysite.com",
  },
  spamProtection: {
    honeypot: true,
    rateLimit: { maxSubmissions: 5, windowMs: 60_000 },
  },
});

export default defineConfig({
  plugins: [fb.plugin],
  collections: [Posts, Users, Media],
});
```

**2. Define the form fields (code-first):**

```typescript
import {
  text,
  email,
  textarea,
  select,
  checkbox,
  option,
  hidden,
  createFormConfig,
} from "@nextlyhq/plugin-form-builder";

const contactForm = createFormConfig("contact", [
  text({ name: "name", label: "Full Name", required: true }),
  email({ name: "email", label: "Email", required: true }),
  select({
    name: "subject",
    label: "Subject",
    required: true,
    options: [
      option("General Inquiry"),
      option("Support"),
      option("Partnership"),
    ],
  }),
  textarea({
    name: "message",
    label: "Message",
    required: true,
    rows: 5,
    validation: { maxLength: 5000 },
  }),
  checkbox({ name: "newsletter", label: "Subscribe to updates" }),
  hidden({ name: "source", label: "Source", defaultValue: "website" }),
]);
```

`createFormConfig` builds the definition and stops there. Nothing in the plugin accepts
a `FormConfig`: `formBuilder()` takes no `forms` option, and `submitForm` resolves a slug
by querying the **forms collection**, so a form exists at submission time only as a row in
that collection. Create the `contact` form in the admin under Forms before going further,
or seed the row yourself; a submission to a slug with no row is answered as a form that
does not exist, before validation or storage. Closing that gap is tracked as
`createFormConfig` having no path to a row.

**3. Handle submissions in an API route:**

`submitForm` takes two context values: `pluginContext`, which is a plugin's `ctx`, and
`pluginConfig`, which is the resolved form-builder config. Both are reachable from your
own config file. A route contributed through [`contributes.routes`](/docs/plugins/routes)
is handed the `ctx` as its second argument, and `formBuilder()` returns its resolved
config as `fb.config`, which is why step 1 keeps the return value rather than inlining it.

So the endpoint is a small plugin of your own, declared beside the form-builder in
`nextly.config.ts`:

```ts
// nextly.config.ts
import {
  defineConfig,
  getTrustedClientIp,
  parseTrustedProxyIpsEnv,
} from "nextly";
import { definePlugin } from "@nextlyhq/plugin-sdk";
import { formBuilder, submitForm } from "@nextlyhq/plugin-form-builder";

const fb = formBuilder({
  notifications: { defaultFrom: "noreply@mysite.com" },
  spamProtection: {
    honeypot: true,
    rateLimit: { maxSubmissions: 5, windowMs: 60_000 },
  },
});

const contactEndpoint = definePlugin({
  name: "@acme/contact-endpoint",
  version: "1.0.0",
  nextly: ">=0.0.2-alpha.63",
  contributes: {
    routes: [
      {
        method: "POST",
        path: "/contact",
        // A visitor has no session, so the route opts out of auth. What stops
        // abuse is `submitForm` itself: the honeypot and rate limit configured
        // above run on every call, and a route that skipped it would skip them.
        public: true,
        handler: async (request, ctx) => {
          const data = await request.json();

          // Through the trust-proxy gate, never straight off the header: this
          // value keys the rate limit above, so a forgeable one hands a bot a
          // fresh bucket per request. `null` becomes `undefined`, which the
          // limiter reads as "cannot attribute" and skips.
          const ipAddress =
            getTrustedClientIp(request, {
              trustProxy: ctx.config.security?.trustProxy ?? false,
              trustedProxyIps: parseTrustedProxyIpsEnv(
                process.env.TRUSTED_PROXY_IPS
              ),
            }) ?? undefined;

          const result = await submitForm(
            {
              formSlug: "contact",
              data,
              metadata: {
                ipAddress,
                userAgent: request.headers.get("user-agent") ?? undefined,
              },
            },
            { pluginContext: ctx, pluginConfig: fb.config }
          );

          return Response.json(result);
        },
      },
    ],
  },
});

export default defineConfig({
  plugins: [fb.plugin, contactEndpoint],
  // collections: [...] as in step 1
});
```

The route is mounted under the contributing plugin's namespace, so the form posts to
`/admin/api/plugins/@acme/contact-endpoint/contact` in a scaffolded app, where `/admin/api`
is wherever `createDynamicHandlers` is mounted.
