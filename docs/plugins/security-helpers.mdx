# Security helpers

> **Alpha (`0.x`) — `@experimental`.** Everything on this page is new and ships
> `@experimental`: it works and is tested, but stays experimental until a
> first-party plugin signs people in with it. Pin your `nextly` and
> `@nextlyhq/plugin-sdk` versions while you build on it.

A plugin that signs in people of its own, such as a shop's customers, needs the
same care with their secrets that core takes with staff. These helpers lend it
core's implementation, so a plugin never writes its own password hashing,
session tokens or reset links. They are on the plugin's context as
`ctx.security`, and their types come from `@nextlyhq/plugin-sdk`.

They serve a plugin's own people only. Staff passwords keep core's own
hashing, and an app's `passwordHasher` option is never used by these helpers:
a plugin's people never share a hashing format with staff.

## Passwords

`ctx.security.passwords` hashes a password, verifies one against a stored
hash, says whether a stored hash should be rehashed, and checks a new password
against your rules.

```ts
import {
  definePlugin,
  PasswordTooLongError,
  type PasswordHelper,
} from "@nextlyhq/plugin-sdk";

/** Sign-up: check the password, then store only its hash. */
async function signUp(passwords: PasswordHelper, password: string) {
  const checked = await passwords.check(password, { breached: true });
  if (!checked.ok) return { error: checked.reason };
  try {
    return { hash: await passwords.hash(password) };
  } catch (error) {
    if (error instanceof PasswordTooLongError) return { error: "too-long" };
    throw error;
  }
}

/** Sign-in: verify, and move an old hash to today's setting. */
async function signIn(
  passwords: PasswordHelper,
  password: string,
  stored: string | null // null when no account has this address
) {
  // With null, verify still spends a real verification's time, so how long
  // the answer takes never tells a visitor whether the account exists.
  const ok = await passwords.verify(password, stored);
  if (ok && stored !== null && passwords.needsRehash(stored)) {
    return { ok, newHash: await passwords.hash(password) };
  }
  return { ok };
}

export default definePlugin({
  name: "@acme/accounts",
  version: "1.0.0",
  nextly: ">=0.0.2-alpha.67",
  init(ctx) {
    ctx.logger.info(`passwords up to ${ctx.security.passwords.ceiling} characters`);
    void signUp;
    void signIn;
  },
});
```

### What `hash` guarantees

- **Every character counts.** The whole password is hashed after Unicode NFC
  normalisation, so two passwords that differ only past the 72nd byte never
  verify against each other's hash, and a composed and a decomposed form of the
  same text verify alike. Compatibility-distinct characters stay distinct: a
  full-width letter is not its ordinary form.
- **Well-formed Unicode only.** A password holding a lone surrogate, as JSON
  can carry one, is refused by `hash` and `check` with a validation error and
  never verifies: encoded to UTF-8, every lone surrogate becomes the same
  character, so two different passwords would otherwise hash alike.
- **A ceiling, never a cut.** A password longer than `ceiling` (256 code points)
  throws `PasswordTooLongError`, and `verify` answers false for one; neither ever
  cuts a password to fit.
- **The algorithm.** scrypt from `node:crypto`, at N = 2^15, r = 8, p = 3: a
  setting OWASP's Password Storage Cheat Sheet lists, 32 MiB a hash, deriving
  32 bytes from a fresh 16-byte salt. Expect around 150 ms a hash on a
  developer machine, more on a small server.
- **The stored string.** At most 255 ASCII characters, naming its algorithm and
  setting. Size your column for 255, and treat the string as opaque: its format
  inside may change.

### What `verify` and `needsRehash` answer

- `verify` answers false for a wrong password, a malformed hash, and a hash it
  did not write (a staff bcrypt hash among them), and never throws for any of
  them. A hash it cannot read is logged as a warning, without the hash or the
  password.
- `verify(password, null)` spends a real verification's time and answers false.
  Call it when no account matches, so the response time is the same either way.
- `needsRehash` answers true for any string that is not a hash at today's
  setting, a format the helper does not know included. When it does after a
  successful sign-in, hash the password again and store the new hash: that is
  how a stored hash moves to a later setting.

### Checking a new password

`check(password, rules?)` goes by length and lists, never by the kinds of
characters a password holds: a long password of lowercase letters is accepted.

| Rule | Bounds | Default |
| --- | --- | --- |
| `minLength` | 8 to 64 code points | 8 |
| `maxLength` | 64 to 256 code points | 128 |
| `breached` | `true` or `false` | `false` |

Rules outside their bounds throw a validation error naming the rule and its
bounds. Lengths are counted in code points after NFC, as NIST SP 800-63B
counts them, so an emoji is one character.

Every check also refuses the 3,000 most common passwords of 8 characters or
more, compared without regard to case. The list is the UK NCSC's list of the
passwords seen most often in Have I Been Pwned's breach data, as SecLists
publishes it.

The answer is `{ ok: true, breachedCheck }` or `{ ok: false, reason }`, where
`reason` is `"too-short"`, `"too-long"`, `"common"` or `"breached"`, and
`breachedCheck` is `"passed"`, `"skipped"` (the check was not asked for) or
`"unavailable"`.

### Breached passwords

With `breached: true`, the check also asks the site's breached-password source,
set in `nextly.config.ts`:

```typescript
security: {
  breachedPasswords: {
    // "pwned-passwords" (the default), { url: "https://…" }, or a list you hold:
    source: "pwned-passwords",
    timeoutMs: 2000,
  },
},
```

- `"pwned-passwords"` asks Have I Been Pwned's range service at its public
  address.
- `{ url }` asks a range service at `<url>/<prefix>`. It must be `https`: any
  other address is sent nothing, every check answers `"unavailable"`, and boot
  logs a warning.
- `{ range(prefix) }` asks a list you hold, in the process: it receives the
  prefix and answers with the suffixes it knows.

Only the first 5 hex digits (20 bits) of the password's SHA-1 ever leave the
process. A range service is asked with a user agent naming Nextly, as Have I
Been Pwned asks of every client, and for padded answers, so the size of the answer
says nothing about the prefix. When the source fails, answers with an error, or
does not answer within `timeoutMs` (1 to 60,000 ms; another value is named at boot and replaced by the default of 2,000), or answers with anything that is not a list of suffixes, the password is accepted with
`breachedCheck: "unavailable"`: a source that is down neither locks people out
nor pretends to have checked. Decide what your plugin does with an unchecked
password; asking again on the next sign-in is a reasonable choice.

## Opaque secrets

`ctx.security.opaque` makes random secrets a plugin stores only as a hash,
such as its own session tokens or API keys.

```ts
import type { OpaqueSecrets } from "@nextlyhq/plugin-sdk";

/** Start a session: the browser gets the secret, the database its hash. */
function newSession(opaque: OpaqueSecrets) {
  const { secret, hash } = opaque.create();
  return { cookieValue: secret, storedHash: hash };
}

/** Find the session a cookie names, by the hash of what it presents. */
function sessionKey(opaque: OpaqueSecrets, cookieValue: string) {
  return opaque.hash(cookieValue);
}
```

- `create()` returns 32 random bytes as base64url, with their SHA-256 in hex.
  Pass `{ bytes }` for a longer secret, at most 1024. Any other size, under 32, over 1024 or not a whole number, is refused with a validation error and nothing is
  issued.
- `hash(secret)` gives the hash `create` gave, every time. It has no key, so it
  stays the same across restarts and when the install's secret rotates: your
  stored hashes never go stale. A key would add nothing to 256 random bits,
  which cannot be found by trying values.
- `equal(a, b)` compares two values in time that depends only on their lengths,
  for when you hold both rather than looking one up by its hash.

## One-purpose secrets

`ctx.security.secrets` mints and spends secrets that do one thing once: a long
token for a link, such as a password reset, or a short code a person types,
such as a sign-in code. Each has a `purpose` and a `subject`, such as an
account id, and only the plugin that minted it can read or spend it.

### A link: password reset

```ts
import type { PluginContext } from "@nextlyhq/plugin-sdk";

const HOUR = 60 * 60 * 1000;

/** Forgot password: a link that works once, for an hour. */
async function resetLink(ctx: PluginContext, accountId: string) {
  const { token } = await ctx.security.secrets.mintToken({
    purpose: "password-reset",
    subject: accountId,
    expiresInMs: HOUR,
    voidEarlier: true, // an earlier link stops working
  });
  return `https://shop.example/reset?token=${encodeURIComponent(token)}`;
}

/** Reset: spend the link and change the password in one transaction. */
async function resetPassword(ctx: PluginContext, token: string) {
  return ctx.db.transaction(async tx => {
    const spent = await ctx.security.secrets.consumeToken(
      { purpose: "password-reset", token },
      { tx }
    );
    if (!spent.ok) return { error: spent.reason };
    // Store the new hash for spent.subject here, through tx. If anything in
    // this transaction fails, the spend rolls back too and the link still works.
    return { accountId: spent.subject };
  });
}
```

`peekToken` reads a token without spending it, for a page that shows what a
link will do before the person confirms. Both answer `invalid`, `expired` or
`spent` when they refuse, and never say whether the subject exists. Inside
your own transaction, pass it `{ tx }` too, so it reads what that transaction
wrote; without one it is refused while a transaction is open, as a write is,
so a read answers the same on every database.

### A code: sign in by email

```ts
import type { PluginContext } from "@nextlyhq/plugin-sdk";

/** Send a 6-digit code, good for 10 minutes and 5 wrong tries. */
async function sendCode(ctx: PluginContext, email: string) {
  const { code } = await ctx.security.secrets.mintCode({
    purpose: "sign-in",
    subject: email,
    expiresInMs: 10 * 60 * 1000,
    maxWrongTries: 5,
  });
  return code; // mail it; a new code voids the earlier one
}

/** Check the code first, then do what it allows. */
async function signInWithCode(ctx: PluginContext, email: string, code: string) {
  const answer = await ctx.security.secrets.consumeCode({
    purpose: "sign-in",
    subject: email,
    code,
  });
  if (!answer.ok) {
    return answer.reason === "wrong"
      ? { error: "wrong", triesLeft: answer.triesLeft }
      : { error: answer.reason }; // "none", "expired" or "spent"
  }
  return ctx.db.transaction(async () => {
    // Create the session here. If this transaction fails, the code stays
    // spent: ask the person to request a new one.
    return { signedIn: email };
  });
}
```

Spend a code first, then open the transaction that applies its effect.
`consumeCode` takes no transaction, and throws when the calling flow has one
open: a wrong code's charge must stand even if a later step rolls back, or a
visitor could guess without limit by making each attempt fail. The cost is that
a code whose effect fails stays spent, and the person asks for a new one.

### What they guarantee

- **Stored only as a keyed hash.** A token or code is kept as an HMAC under a
  key derived from the install's secret for this use alone, so a copy of the
  database cannot recover even a 6-digit code by trying every value. When the
  install's secret rotates, a secret minted under the previous one still works
  while that secret is configured for reading.
- **Spent once, on every instance.** Spending is one conditional write in the
  database, so of two spends at once, on one server or two, exactly one
  succeeds. A code's wrong tries are counted the same way, so a burst of
  guesses across instances never gets more than the code's budget.
- **One live code.** A new code for a purpose and subject voids the earlier
  one, and if two are minted at once, exactly one is live afterwards. Tokens
  are voided only when you pass `voidEarlier`, or call `voidFor`; two replacing
  mints at once also leave exactly one token live.
- **Writes in a transaction.** Pass `{ tx }`, the handle `ctx.db.transaction`
  gives its callback, and a mint, spend or void commits or rolls back with your
  work. Without it the write runs in a transaction of its own, and is refused
  with an error if the calling flow already has a transaction open, rather than
  silently joining it.
- **Swept after expiry.** The retention runner removes a secret a day after it
  expires, spent or not. Writes offer the sweep and so does the scheduled drain,
  so an install that only mints secrets, or goes quiet, still sweeps them and the
  table does not grow without bound. Until then an expired secret still answers
  `expired`.

### Bounds

| Input | Bound |
| --- | --- |
| `purpose` | a lowercase letter, then up to 63 lowercase letters, digits, dots or hyphens |
| `subject` | 1 to 255 characters of well-formed Unicode, with no NUL character; compared exactly, case and spaces included, on every database |
| a token's `expiresInMs` | 1 minute to 30 days |
| a code's `expiresInMs` | 1 to 60 minutes |
| `digits` | 6 (the default), 7 or 8 |
| `maxWrongTries` | 1 to 10 |
| `data` | a plain object (not a `Date` or class instance) holding strings, finite numbers, booleans and nulls, at most 1 KB as JSON, stored in clear |

A value outside its bound is refused with a validation error before anything
is written. Keep secrets out of `data`: it is stored as given and returned to
whoever spends the secret.

## Building a context by hand

`ctx.security` is a required member of `PluginContext`. A context from
`createTestNextly` (`@nextlyhq/plugin-sdk/testing`) has the real helpers; a
test double you build yourself needs a `security` member of its own.
