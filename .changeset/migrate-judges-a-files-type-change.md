`nextly migrate` now judges a migration file's field type change by the values the database it runs on holds, as the Schema Builder save that wrote the file judged it, before the file's first statement. A value the new type cannot read stops the run, naming the field, its rows and the file, where before SQLite kept the value in the new column and PostgreSQL and MySQL failed part-way. The dry run lists the same refusal. There is no consent yet that clears such values on `nextly migrate`: `--accept-data-loss` still covers the column's deletion mark, not the values that cannot convert.
