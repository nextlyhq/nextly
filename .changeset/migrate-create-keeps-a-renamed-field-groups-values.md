`nextly migrate:create` now asks whether a renamed field group (`fieldGroup({ name })` in your config, including a repeatable one or a list of several groups) is a rename, as it does for a renamed column. Accept it and the migration moves the field's stored values to the new name, with the reverse in its `DOWN`. Before, the migration moved nothing and the renamed field read empty after `nextly migrate`, its values left under the old name. With no terminal, `--accept-renames` accepts it; without that flag it is declined and `migrate:create` warns that the values stay under the old name.
