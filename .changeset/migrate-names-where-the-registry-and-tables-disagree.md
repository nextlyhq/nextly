`nextly migrate`, once it finishes, and `nextly migrate:status` now name every place the registry and the database disagree: a registry row whose table does not exist, a field a registry row records whose column does not exist (such as a plugin's new field whose column was never added), and a collection, single or field group the configuration declares that has no registry row. Both only read, and neither changes its exit code for what it names. `migrate:status --json` carries the findings under a new `registry` key. Nothing at server start makes this comparison, so a deployment that runs neither command does not see it: run `nextly migrate` (or `nextly migrate:status`) where you deploy.
