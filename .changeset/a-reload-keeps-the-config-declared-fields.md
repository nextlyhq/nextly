A reload of the definitions keeps the fields the configuration declares, as the start does. Where an entity's registry row predates its configuration (a build whose new field the registry row does not hold yet), the start registers the configuration's definition over the row's, but a reload, such as the Direct API's first schema-version follow or the reload after boot migrations, loaded the row's narrower definition alone. A declared field the table holds was then no longer served, and one the database was not migrated for was no longer reported as not migrated. Every reload now registers the configuration's entities after the rows, through the start's own step.
